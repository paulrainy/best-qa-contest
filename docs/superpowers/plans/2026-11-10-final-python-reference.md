# Эталон проекта автоматизации на Python — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Создать полноценный Python-эталон построения автоматизации с нуля и отдельное задание для Python-направления.

**Architecture:** Участник получает Markdown-условие, контракт и готовый стенд. Жюри получает самостоятельный pytest-проект с подготовкой данных, проверками HTTP/AMQP/БД, воспроизводимой установкой и отчётом. Глубина покрытия совпадает с Java по общему каталогу F01–F18.

**Tech Stack:** Python 3.11, uv с `uv.lock`, pytest 9.1.1, requests 2.34.2, pika 1.4.4, psycopg 3.3.8 с binary extra, стандартный `decimal`. Версии закрепляются и проверяются на Python 3.11; совместимость с Windows/ВДИ подтверждается отдельно, а не предполагается из прогона Mac.

**Spec:** [Общие требования и предложения для согласования](../specs/2026-11-10-final-four-directions-design.md).

**Статус:** не согласован, исполнение не начато.

## Global Constraints

- Базовые версии — Java 17 и Python 3.11. Сборки и проверки выполняются на этих версиях; более новые версии не заменяют такую проверку. Python не обязателен для участника ручного направления.
- Направление — `final-task/1d-python/`, сопоставление с рейтинговым 1d сохраняется.
- До этого плана выполняются только общие этапы 1–2 [Java-плана](2026-11-10-final-java-reference.md). Сам Java-эталон не является зависимостью.
- `participant/` содержит README, ТЗ и готовую runtime-копию стенда, без `starters/` и готовых тестов.
- Полный эталон, lock-файл и доказательства находятся только в `jury/reference/`.
- Базовый набор не требует UI, Kafka, Docker, параллельного запуска pytest или Allure-сервера.
- Баллы и штрафы по этому плану не вводятся. Реализация начинается после согласования.

## Review Focus

1. Нет доступного PostgreSQL-порта: fixture завершается с понятной причиной, а не имитирует найденный дефект — этапы 2 и 4.
2. AMQP-сообщение не приходит или относится к другому переводу: ожидание ограничено, чужое сообщение не принимается за доказательство — этапы 2–3.
3. Округление и сериализация денег не используют `float` как источник ожидаемых сумм — этап 3.
4. Падение внутри сценария с часами или потребителем не оставляет стенд изменённым — этапы 2–3.
5. Пропущенный тест, неизвестная ошибка и устаревший отчёт не проходят контроль ожидаемых результатов — этап 4.

## Этап 2. Помощники и жизненный цикл ресурсов

**Интерфейсы:** `load_config(path: Path) -> StandConfig` читает URL/логины/порты из INI; `Api.create_account(balance: Decimal, client_id: str | None, status: str) -> dict`; `Api.transfer(src: str, dst: str, amount: Decimal, key: str) -> requests.Response`; `wait_final(api: Api, transfer_id: str, timeout_s: float = 10) -> dict`; `Events.subscribe(channel, routing_key: str) -> Events`; `Events.wait(transfer_id: str, event_type: str, timeout_s: float = 10) -> dict`; `Db.postings(transfer_id: str) -> list[dict]`. Ключи JSON/строк БД определены в общем ТЗ; отдельная библиотека моделей не требуется.

- [ ] Перед помощником ожиданий написать содержательный тест: заданная последовательность `PROCESSING, COMPLETED` завершается, вечный `PROCESSING` даёт timeout с идентификатором; использовать управляемые ответы и часы ожидания, не настоящую десятисекундную паузу в unit-тесте.
- [ ] Перед реализацией cleanup написать тест исключения внутри fixture/context manager: соединение закрывается, управляемые часы возвращаются, остановленный потребитель возобновляется. Не подменять этим последующую интеграционную проверку реального стенда.
- [ ] Реализовать HTTP-клиент с таймаутами, AMQP-наблюдатель с временной очередью, psycopg-подключение только для SELECT и параметризованные запросы. Подписка создаётся до перевода, ресурсы освобождаются через `yield`/`finally`.
- [ ] Передавать деньги в запросе как JSON number из точного десятичного представления; ожидаемые суммы и сравнения хранить в `Decimal`. Не сериализовать `Decimal` простой заменой на строковый тип поля, противоречащий ТЗ.
- [ ] В `conftest.py` разделить обычные данные теста и выделенную область для сценариев с глобальными часами/паузами. Обычный тест не вызывает reset; глобальные сценарии выполняются последовательно и всегда восстанавливают настройки.
- [ ] Запустить `uv run pytest tests_support -q`, затем один реальный F02 с новым клиентом и двумя счетами: API, AMQP и БД должны показать одно зачисление 100,00 и корректные остатки.

## Этап 3. Покрытие F01–F18

**Выход:** бизнес-тесты и `traceability.md` с соответствием «правило → группа F → test node ID → доказательство». Число параметров не превращается в отдельные баллы.

- [ ] Реализовать F01–F08: smoke, `OWN`/`OTHER`, суммы, формат, неизвестные счета, матрица статусов, запрет самоперевода и граница дневного лимита. Для границ использовать параметризацию и свежие данные каждого варианта.
- [ ] Реализовать F09, F11–F15, F17–F18: полночь МСК, комиссия после порога, идемпотентность/24 часа, событие, SQL-проводки, асинхронные состояния, уведомления, оборот. Не использовать внутренние классы стенда.
- [ ] В тесте `tests/test_commission.py::test_threshold_crossing_charges_only_excess` проверить F10: после 90 000,00 перевод 20 000,00 должен иметь комиссию 100,00. Метка `known_issue` документирует известное отклонение; assert по правильному результату остаётся активным и содержит диагностический текст `KNOWN:F10:COMMISSION`.
- [ ] В `tests/test_async.py::test_failed_transfer_refunds_amount_and_commission` проверить F16 по независимой подготовке: успешные 100 000,00, затем 40 000,00 с комиссией 400,00, закрытие получателя до обработки. Проверить полный возврат по остатку и проводке; целевой assert содержит `KNOWN:F16:REFUND`, ошибки подготовки/HTTP/ожидания эту метку не используют.
- [ ] Зарегистрировать `known_issue` в настройках pytest и включить строгую проверку имён маркеров. Не использовать `skip`, нестрогий `xfail`, перехват любого исключения или повторные прогоны до случайного успеха.
- [ ] Выполнить полный набор дважды и обычные сценарии в другом порядке; сравнить состав результата. Полный прогон ожидаемо имеет два конкретных assertion failure; все остальные проверки проходят без ошибок коллекции, подключения и teardown.
