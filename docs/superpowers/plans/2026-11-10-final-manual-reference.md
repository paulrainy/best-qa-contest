# Эталон проекта ручного тестирования — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Создать полный исполненный образец ручного покрытия сервиса с нуля и отдельное задание для ручных тестировщиков.

**Architecture:** Участник получает продуктовый контракт, готовый стенд и Markdown-инструкции. Эталон жюри показывает анализ рисков, тест-дизайн, воспроизводимые кейсы, исследовательские сессии, SQL-сверку и фактический отчёт. Доказательства получают через открытые интерфейсы стенда; готовый код проверки или внутренний ключ не заменяет ручное исполнение.

**Tech Stack:** Markdown, HTTP-клиент по выбору исполнителя, веб-консоли брокера/H2 и читающий SQL-клиент. Java 17 или Java 21 нужна только для запуска стенда. Автоматизация, Python и написание собственного инструмента не являются обязательными для ручного направления.

**Spec:** [Общие требования и предложения для согласования](../specs/2026-11-10-final-four-directions-design.md).

**Статус:** полный повтор на новой сборке95af5243…875377 завершён: M01–M18 PASS, EX/SQL и другой порядок исполнены. Независимая проверка остаётся открытой, см. текущий report.md.

## Global Constraints

- Базовые версии — Java 17 и Python 3.11; обязательна совместимость с Java 21 и актуальными стабильными версиями CPython новее 3.11. Проверки совместимости дополняют базовые. Python не обязателен для участника ручного направления.
- Направление — `final-task/1b-manual/`, соответствует рейтинговому 1b.
- Зависимость — только общие этапы 1–2 [Java-плана](2026-11-10-final-java-reference.md). Готовность Java/Python-тестов не требуется.
- Инструкции, кейсы и объяснения эталона оформляются в Markdown. Отдельные XLSX/DOCX/PPTX не обязательны.
- Цель — обоснованное ручное покрытие проекта; нет требования найти заданное количество багов или воспроизвести экзотические сценарии.
- Общая глубина функционального покрытия — F01–F18. Техническая форма решения свободна, копирование эталона не является критерием качества.
- Сырые доказательства могут иметь исходные форматы: ответы JSON, SQL-результаты CSV, скриншоты. Текстовое объяснение каждого доказательства находится в Markdown.
- Реализация начинается после согласования; балльная шкала в этот план не входит.

## Review Focus

1. Другой тестировщик не знает номера исходных счетов: кейс сам задаёт подготовку данных и ожидаемые остатки — этапы 2–3.
2. Асинхронная операция ещё не завершилась: кейс различает `PROCESSING`, timeout и продуктовый отказ — этапы 2–3.
3. Глобальные часы или потребитель остались изменены после сессии: описана и проверена очистка — этапы 2–3.
4. Комиссия и полный возврат проверяются независимо: подготовка F16 использует уже исчерпанный порог — этап 3. Намеренных дефектов в новой сборке нет.
5. Красивые документы без фактического исполнения не принимаются как полный эталон — этапы 3–4.

## Этап 1. Условие направления и стратегия эталона

**Вход:** готовый стенд и общий каталог F01–F18. **Выход:** понятное задание участника и объяснение границ эталона.

- [x] В `participant/README.md` сформулировать задачу: самостоятельно спроектировать и выполнить ручное тестирование нового сервиса, подготовить результаты и обосновать достаточность покрытия.
- [x] В одном README описать запуск, адреса API/консолей/БД, тестовый API, способ подготовки данных, наблюдение статусов и состав сдачи. Не выдавать готовые тест-кейсы, коллекцию с готовыми проверками или скрытые ответы жюри.
- [x] В `test-strategy.md` определить риски: неверное движение денег, лимиты/комиссии, повтор запросов, асинхронные статусы, уведомления и отчёт. Разделить smoke, основную проверку и возможное расширение при наличии времени.
- [x] Исключить обязательные проверки гонок, нагрузку, «ядовитые» сообщения, декомпиляцию и чтение исходников. Сложная эксплуатационная диагностика не требуется для максимального качества ручной работы.

## Этап 2. Дизайн и воспроизводимые кейсы

**Интерфейс кейса:** ID, правило ТЗ и F-группа, цель, приоритет, предусловия, конкретная подготовка, действия, ожидаемый результат каждого значимого действия, очистка, фактический результат и ссылка на доказательство. Фактический результат не заполняется до реального исполнения.

- [x] Построить в `test-design.md` классы и границы суммы/дневного лимита/комиссии; матрицу статусов счетов; переходы `PROCESSING → COMPLETED/FAILED`; варианты идемпотентного повтора. Связать каждую технику с конкретным правилом.
- [x] На основе дизайна написать компактный набор, покрывающий F01–F18. Несколько граничных значений можно оформить таблицей вариантов одного кейса; не раздувать число карточек ради количества. Отдельно отметить минимальный smoke и рискованный регресс.
- [x] В `test-data.md` дать воспроизводимую подготовку через тестовый API: новые клиенты, активные/закрытые/заблокированные счета, точные суммы. Кейс не зависит от запомненного номера сидового счёта или результата предыдущего кейса.
- [x] Для асинхронных кейсов описать наблюдаемое условие завершения, предел ожидания 10 секунд для одиночного перевода без нагрузки и отдельный исход «не завершился за время наблюдения». Само ожидание не является подтверждением правильности проводок.
- [x] Для глобальных действий явно записать возврат часов и возобновление потребителей, в том числе при остановке кейса с ошибкой. Проверить, что следующий контрольный перевод после очистки завершается.
- [x] Сопоставить кейсы с F01–F18 и разделами ТЗ в `traceability.md`. Ожидаемая проверка: нет группы без сценария и нет обязательного сценария, требующего недоступного инструмента.
