# Эталон проекта нагрузочного тестирования — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Создать законченный образец нагрузочного тестирования проекта с нуля: методика, исполняемая нагрузка, исходные измерения, анализ и проверяемый отчёт.

**Architecture:** Участник получает контракт и готовый стенд с метриками. Эталон жюри использует JMeter без сторонних плагинов для независимой подачи `POST`, отдельный сбор метрик и анализ полного набора данных. Принимается достоверность измерений и выводов; выполнение НФТ дефектным стендом не является условием правильности самого нагрузочного проекта.

**Tech Stack:** JMeter 5.6.3, Java 17 и Java 21, Python 3.11+ с базовой версией 3.11 и его стандартная библиотека для запуска/сбора/анализа. Для экспортируемых графиков — matplotlib 3.9.2 как начальная версия из окружения генераторов; при необходимости подобрать совместимые версии по матрице Python, сохранив поддержку 3.11. Docker, Grafana, Prometheus-сервер и AMQP-плагины JMeter не обязательны: `/metrics` читается напрямую.

**Spec:** [Общие требования и предложения для согласования](../specs/2026-11-10-final-four-directions-design.md).

**Статус:** не согласован, исполнение не начато.

## Global Constraints

- Базовые версии — Java 17 и Python 3.11; обязательна совместимость с Java 21 и актуальными стабильными версиями CPython новее 3.11. Проверки совместимости дополняют базовые. Python не обязателен для участника ручного направления.
- Направление — `final-task/1c-load/`, соответствует рейтинговому 1c.
- Зависимость — только общие этапы 1–2 [Java-плана](2026-11-10-final-java-reference.md). Другие три эталона не требуются для начала нагрузочного.
- Участник создаёт собственные методику, скрипт и отчёт; готовый JMX ему не выдаётся.
- Базовый объём БД — 30 000 переводов истории. Цель — 50 новых `POST`/с; p95 принятого `POST` ≤ 500 мс, ≥ 95% принятых переводов завершаются за ≤ 2 с.
- Требование до миллиона строк и обязательная экстраполяция исключены из базовой сложности.
- Документация — Markdown, исполняемый JMX и первичные JTL/CSV/JSONL сохраняют исходные форматы. Результаты ВДИ отдельно от локальных.
- Баллы и веса не задаются. Исполнение только после согласования.

## Review Focus

1. HTTP 200 с прикладным отказом и 503 не принимаются за успешно созданные переводы — этапы 2–3.
2. Незавершённые переводы не исчезают из знаменателя SLO «за 2 секунды» — этапы 3–4.
3. Прогрев, неполный хвост и усреднение оконных p95 не искажают итог — этап 3.
4. Генератор не подал заданные 50 `POST`/с: прогон помечается несостоявшимся для проверки НФТ, а не выдаётся за предел сервиса — этапы 2 и 4.
5. Исчерпание остатков/лимита и служебные GET не смешиваются с целевым бизнес-профилем — этапы 1–2.

- [ ] В эталонной `methodology.md` зафиксировать контролируемый профиль: 100% новых `OTHER` по 100,00 ₽ между разными активными клиентами. Это профиль проверки конкретной системы без статистики прода; не выдавать его за подтверждённое промышленное распределение.
- [ ] Целевую интенсивность считать только по `POST /transfers`. Опрос `/metrics` каждые 5 секунд и сбор финальных статусов описать отдельно; не добавлять их к 50 бизнес-операциям/с.

На каждом новом прогоне стенд сбрасывается до старта нагрузки, не во время неё.

## Этап 2. Рабочий JMeter-проект и сбор доказательств

**Интерфейсы:** `tools/run.py --profile <name> --jmeter <executable> --base-url <url> --output <new-dir>` организует один прогон. Каталог результата новый, существующие измерения не перезаписываются. Сценарии JMX читают настройки из файла профиля, подключение — из свойств, CSV — из `test-data/`.

- [ ] Создать `transfers.jmx` на штатных элементах JMeter 5.6.3: подготовка входных данных, уникальный `Idempotency-Key`, JSON-запрос и проверка одновременно кода и тела. Для принятого перевода требуются 202, `transferId` и `PROCESSING`; 200 `REJECTED` неуспешен, 503 отдельно классифицируется как отказ при перегрузке.
- [ ] Сохранять в JTL время, elapsed, label, success, responseCode и извлечённые `transferId`, `createdAt`. Не писать на каждый запрос полный ответ в память через тяжёлый GUI listener. GET и метрики имеют отдельные labels или отдельные файлы и не входят в статистику `POST`.
- [ ] Подключить CSV с общим чтением строк без повторов одной строки несколькими потоками в одном событии подачи. Проверить уникальность ключей, наличие всех полей и правильность пользовательских данных на smoke-прогоне.
- [ ] Реализовать `collect_metrics.py` с записью временной шкалы: глубины очередей, число обработанных сообщений, завершения, число строк, heap, CPU процесса стенда, доступные HTTP-счётчики. Ошибка сбора записывается как пропуск данных, а не нулевое значение метрики.
- [ ] Реализовать `collect_transfers.py`: из принятых ID в JTL получить через API `createdAt`, `completedAt`, финальный статус. После нагрузки наблюдать drain до 120 секунд; незавершённые операции сохранять отдельными строками. Для SLO использовать исходное время финализации, а не время позднего опроса.
- [ ] Реализовать `run.py`: проверка health, один reset до прогона, запуск сборщика, JMeter CLI, завершение сбора, drain/сбор статусов, вызов анализа. Ошибки запуска и JMeter-процесса не скрываются даже при наличии старых файлов результата.
- [ ] Для raw CLI проверить из каталога эталона: `jmeter -n -t transfers.jmx -q profiles/smoke.properties -l build/smoke/samples.jtl -e -o build/smoke/html`. Каталог HTML должен быть новым/пустым; в Windows используется `jmeter.bat`.
- [ ] Smoke: 2 `POST`/с, 30 секунд. Ожидаются поданная интенсивность, корректные данные, принятые и завершённые операции, читаемые метрики. Успешное завершение процесса JMeter само по себе не означает выполнение критериев.
- [ ] Повторить smoke со стендом и JMeter на Java 21 после базового запуска на Java 17. Для каждой версии CPython из общей матрицы проверить чистую установку зависимостей, запуск/сбор/анализ smoke и построение графиков; сохранить версии и результаты отдельно. Полные нагрузочные профили достаточно исполнить в базовом окружении; сравнение миллисекунд между версиями JVM не является условием совместимости.
- [ ] На управляемом замедлении HTTP или недостатке ресурсов генератора убедиться, что контроль фактической интенсивности обнаруживает недодачу. Убрать временное условие и повторить smoke. Не изменять продуктовый JAR для основного измерения.

## Этап 3. Достоверный анализ полного набора данных

**Интерфейс:** `analyse.py --jtl <file> --metrics <file> --transfers <file> --profile <properties> --output <file>` возвращает машиночитаемое резюме с популяциями и исключениями. Профиль задаёт все измерительные интервалы: для ступеней это [15;60), [75;120), [135;180), [195;240) секунд от начала подачи, для confirmation — [30;180), для stability — [60;600). Когорту определять по времени начала POST из полного JTL; поздний ответ или завершение после конца интервала не удаляет операцию из её когорты. `plot.py --summary <file> --metrics <file> --output <dir>` создаёт экспортируемые графики; оформление не заменяет численные данные.

- [ ] До реализации расчёта написать содержательные тесты в `tests/test_analysis.py`: 20 успешных принятых `POST` с elapsed 100, 200, …, 2000 мс дают nearest-rank p95 = 1900 мс; добавленный timeout, служебный GET и прогрев не меняют p95 этой определённой популяции.
- [ ] Добавить тест SLO: из 10 принятых переводов 7 завершились за ≤ 2 с, 2 позже, 1 не завершился после истечения срока. Результат — 70%, а не 7/9. Отдельно проверить отсутствие окончательных данных и недопустимость приравнивания незавершённых к успешным.
- [ ] Добавить тест классификации: 202 с корректным телом — принято; 200 `REJECTED`, 503, timeout, 202 без `transferId` — разные неуспешные категории. Принятие и завершение считаются отдельно.
- [ ] Добавить тест границ ступеней: первые 15 секунд каждой ступени исключаются, а принятый POST перед концом измерительного окна с поздним завершением остаётся в когорте. Для скорости обработки брать приращения счётчиков между замерами; reset данных не считать обнулением метрик процесса. Сброс самого счётчика обнаруживается как смена сегмента, а не отрицательная скорость.
- [ ] Реализовать итоговый p95 по всем подходящим строкам исходного JTL, не среднее оконных p95 и не ограниченный хвост. Ошибки, отказанные запросы, служебные операции и интервалы прогрева показываются отдельно, с их количествами и причинами исключения.
- [ ] Рассчитать фактические `POST`/с по измерительным интервалам, долю принятых, ошибки, долю завершения за 2 с от принятой когорты, очередь и скорость обработки. Определять нарушение SLO по времени от создания, включая незавершённые после deadline.
- [ ] Проверить непротиворечивость: число извлечённых принятых ID совпадает с принятыми JTL-строками, ID уникальны, все принятые имеют результат/отметку незавершённости. Пропуски данных делают соответствующий вывод недоказанным.
- [ ] Запустить `python -m unittest discover -s tests -v`; затем сверить резюме smoke с ручным пересчётом небольшой выборки JTL и API. Внешний HTML dashboard использовать как дополнительное представление, не как единственный источник правильности.

## Этап 4. Основные прогоны и итоговый отчёт

**Предлагаемый объём эталона:** три основных прогона после smoke, без часов искусственного soak и без миллиона записей. Конкретная интенсивность стабильности подписывается фактическим окружением.

| Профиль | План | Прогрев и измерение |
| --- | --- | --- |
| `steps` | 10 → 20 → 35 → 50 `POST`/с, по 60 с на ступень | Первые 15 с каждой ступени — переход; отдельно 45 с измерения |
| `confirmation` | 50 `POST`/с, 180 с | Первые 30 с — прогрев, следующие 150 с — подтверждение НФТ |
| `stability` | Предварительно 20 `POST`/с, 600 с | 60 с прогрева, 540 с измерения; если это выше найденного устойчивого предела, выбрать около 60% предела и явно записать новое значение |

- [ ] Выполнить `run.py` для трёх профилей с отдельными каталогами; перед каждым — reset, стандартная история 30 000 и восстановленные реальные часы. Не сохранять данные предыдущего прогона как начало нового.
- [ ] Проверить подачу нагрузки: в полных измерительных интервалах фактические новые POST соответствуют заданным в пределах ±5%; недодача требует разбора генератора и не подтверждает выполнение НФТ. При стохастическом arrivals отдельно учитывать допустимую статистическую вариацию коротких окон; для подтверждения оценивать весь измерительный интервал.
- [ ] Зафиксировать ресурсы генератора и стенда, активные потоки и фактическую интенсивность. Если оба на одной машине, явно записать ограничение и не выдавать вывод за промышленную производительность.
- [ ] Для подтверждения сравнить p95 и долю завершений с НФТ. На согласованном стенде ожидается рост очереди учёта и нарушение SLO завершения; точную пропускную способность заранее не подставлять вместо измерения. Корректные 503 при переполнении очереди учитываются как отказы в приёме.
- [ ] Для стабильности проверить отсутствие устойчивого роста очереди, деградации времени ответа и необъяснимого роста памяти на выбранной интенсивности. Десятиминутный прогон не объявлять доказательством суточной устойчивости или отсутствия утечек.
- [ ] Сформировать графики фактической подачи/приёма/ошибок, очереди и разбора, задержки завершения и ресурсов. Рядом с выводами дать ссылки на исходные файлы и интервалы; не усреднять p95 разных окон.
- [ ] В `report.md` описать цель, модель, данные, окружение, каждый прогон, сравнение с НФТ, узкое место и ограничения. В `limitations.md` отдельно указать отсутствие проверки ВДИ/другой платформы, миллиона записей и длительной эксплуатации, если они не выполнялись.
- [ ] В `traceability.md` связать каждый пункт НФТ с профилем, расчётом и доказательством. В `defense.md` объяснить выбор нагрузки и способ отделить ограничение сервиса от генератора; не требовать списка дефектов как главного результата.
- [ ] Другой исполнитель повторяет smoke и confirmation по одному README; сравнивает наблюдаемое поведение и расчёты, а не требует одинаковых миллисекунд на разном железе. При официальном пилоте повторить на целевом ВДИ и сохранить его отдельным набором доказательств.
- [ ] Отобрать реальные JTL, CSV, JSONL, summary и графики в `evidence/`, проверить отсутствие кэшей/эталонов в выдаче. Зафиксировать наблюдения для будущей шкалы без назначения баллов; после проверки оформить сфокусированный коммит.

## Документация инструментов

При планировании проверены [CLI JMeter](https://github.com/apache/jmeter/blob/master/src/core/src/main/resources/org/apache/jmeter/help.txt), [генерация отчёта](https://github.com/apache/jmeter/blob/master/src/core/src/main/java/org/apache/jmeter/JMeter.java) и [Open Model schedule](https://github.com/apache/jmeter/blob/master/src/core/src/main/kotlin/org/apache/jmeter/threads/openmodel/scheduleParser.kt). До реализации синтаксис профилей и загрузка JMX проверяются именно в закреплённом JMeter 5.6.3, а не только по актуальной ветке документации.
