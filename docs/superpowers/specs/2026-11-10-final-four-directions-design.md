# Финальное задание: четыре направления и четыре эталонных решения

**Статус на 11.11.2026:** общая основа, Java-план и ручной план реализованы; результаты и ограничения — в [отчёте Java](../../../final-task/1a-java/jury/reference/report.md) и [ручном отчёте](../../../final-task/1b-manual/jury/reference/report.md). Ручная независимая выборка пройдена, замечание M13 исправлено. Нагрузочный и Python-эталоны ожидают отдельного исполнения. Пилот Windows/ВДИ до официальной выдачи остаётся открытым.

## Требования пользователя

- Четыре направления, соответствующие рейтинговым заданиям: Java, ручное тестирование, нагрузочное тестирование, Python.
- Участник с нуля строит автоматизацию, ручное покрытие или нагрузочное тестирование проекта. Количество найденных дефектов не является целью задания.
- Для жюри нужны четыре полных, проверенных эталонных решения. Шкалу оценки составляем после их проверки.
- Каждое направление получает собственный самодостаточный комплект со скомпилированным стендом в репозитории.
- `starters/` удаляется. Информация для участника оформляется в Markdown.
- По последующему решению пользователя намеренные дефекты полностью удаляются; задание сохраняет умеренную сложность и цель построить тестирование с нуля.
- Каждый из четырёх планов согласуется с пользователем до начала его исполнения.
- Базовые версии — Java 17 и Python 3.11; обязательна совместимость с Java 21 и актуальными стабильными версиями CPython новее 3.11. Проверки совместимости дополняют базовые. Python не обязателен для участника ручного направления.

Стенд и Java-эталон собираются на JDK 17 с `release=17`; одни и те же готовые JAR стенда проверяются на Java 17 и Java 21. JMeter также проверяется на обеих версиях Java. Python-эталон и все служебные Python-инструменты используют возможности Python 3.11 и допускают запуск на старших версиях: `requires-python = ">=3.11"`, без искусственной верхней границы. `.python-version` со значением `3.11` задаёт версию по умолчанию; README объясняет явный выбор другого интерпретатора.

Список проверяемых стабильных версий CPython фиксируется на дату приёмки по релизам начиная с 3.11. Для каждой проверяются установка зависимостей и соответствующие прогоны, а не только разбор исходников. Общий lock-файл при необходимости содержит разные версии зависимостей с маркерами Python; совместимость с 3.11 сохраняется. После выхода новой версии Python проверка повторяется. Фактические версии среды и результаты матрицы фиксируются в доказательствах прогонов.

## Решения общей основы

Эти решения приняты в составе разрешённого пользователем первого Java-плана. Приёмка отдельных эталонов фиксируется в их планах и отчётах; готовность всех четырёх из этого документа не следует.

1. Имена каталогов сохраняют связь с рейтингом: `1a-java`, `1b-manual`, `1c-load`, `1d-python`.
2. Один общий исходный код стенда и одна сборка; одинаковые готовые бинарники физически копируются в четыре комплекта. Ссылки и симлинки между комплектами не используются.
3. Все четыре комплекта используют один функциональный контракт. Java и Python имеют одинаковую глубину покрытия; различаются реализация и инструменты.
4. По последующему решению пользователя намеренные отклонения F10/F16/Н1 удалены: комиссия берётся только с превышения, FAILED возвращает сумму и комиссию, учёт не замедляется искусственно. Эталоны оценивают покрытие исправного продукта; обязательных находок и квоты дефектов нет.
5. Убираем намеренные противоречия ТЗ и ловушки. Описываем однозначные правила и небольшую предметную область. Переход на миллион записей, гонки, генерация «ядовитых» сообщений и восстановление очереди не входят в обязательную работу участника.
6. Обязательная автоматизация покрывает HTTP API, одно событие AMQP и сверку БД. UI, Docker, Kafka, развёртывание Grafana и установка внешнего RabbitMQ не требуются.
7. Бинарники стенда и его зависимости хранятся через Git LFS по аналогии с комплектом 1c. Для запуска готового стенда Maven и сеть не нужны; поддерживаются Java 17 и Java 21. Установка зависимостей эталонов — отдельный, документированный шаг.

## Подход к организации

Выбирается структура, прямо следующая из требования о четырёх самостоятельных каталогах. Общий комплект с выбором трека не даёт четырёх независимых выдач. Четыре отдельные копии исходников стенда усложняют синхронизацию. Поэтому разделяются выдачи и эталоны, а исходники и сборка остаются общими.

```text
final-task/
  README.md                         # только навигация и инструкция организатору
  1a-java/
    participant/
      README.md                     # задание, запуск, подключения, что сдать
      spec.md                       # одинаковый контракт сервиса во всех направлениях
      stand/
        transfer-stand.jar
        lib/                        # runtime JAR и ZIP веб-консоли
        run.cmd
        run.sh
        stand.properties
    jury/reference/                 # полный эталон Java
  1b-manual/                         # такая же выдача; собственный ручной эталон
  1c-load/                           # такая же выдача; собственный нагрузочный эталон
  1d-python/                         # такая же выдача; собственный эталон Python
  jury/
    source/spec.md                  # канонический текст контракта, не выдача
    stand-src/                      # единственные исходники стенда
    build-stand.sh                  # сборка один раз и раскладка четырёх копий
    stand-manifest.md               # хеши исходников сборки и runtime-файлов
    stand-findings.md               # фактические известные отклонения без баллов
    coverage-catalog.md             # общий перечень сценариев F01–F18
    verify/                        # проверки стенда и целостности выдач
    tools/check_reference_results.py # полный зелёный состав Java/Python без исключений
```

В `stand/` нет отдельного README: инструкция находится в `participant/README.md`. `spec.md` описывает продукт, а не повторяет запуск. Старые `participant/`, `starters/` и балльные ключи удаляются после переноса полезной информации и проверки новых комплектов. Ветки и история Git сохраняют прежнюю версию.

Инструкции и объяснения — `.md`. Исполняемые файлы стенда, конфигурация запуска, код эталонов и исходные результаты прогонов сохраняют необходимые им форматы: JAR, ZIP, properties, Java, Python, JMX, CSV, XML, JSONL. Участникам не выдаются тестовые проекты или готовые тесты.

Существующий порядок сдачи за 5 рабочих дней до финала и формат защиты 7 минут + 3 минуты вопросов сохраняются до отдельного решения организаторов. Новые календарные даты в этих планах не придумываются.

## Упрощённый контракт сервиса

Сохранить счета, переводы `OWN`/`OTHER`, комиссию, дневной лимит, идемпотентность, асинхронный учёт, уведомления и оборот. Зафиксировать следующие решения в каноническом ТЗ, затем одинаково скопировать его в четыре выдачи:

- Сумма: 10,00–300 000,00 ₽ включительно, максимум два десятичных знака. Числа разбираются десятично; JSON number сам по себе не объявляется ошибкой требований.
- `ACTIVE`: разрешены списание и зачисление; `BLOCKED`: списание запрещено, зачисление разрешено; `CLOSED`: запрещены оба действия. Убрать юридическую легенду про аресты.
- Перевод со счёта на него же отклоняется как ошибка валидации.
- Дневной лимит `OTHER` — 150 000,00 ₽ включительно без комиссии, сутки по МСК; `FAILED` освобождает лимит.
- Бесплатный порог — 100 000,00 ₽ за календарный месяц по МСК; комиссия рассчитывается только с превышения, в том числе при пересечении порога одним переводом.
- Идемпотентность: ключ глобальный, срок 24 часа; повтор того же запроса возвращает исходный перевод, другой запрос с тем же действующим ключом — 409. Указать, как повтор после 24 часов создаёт новую операцию.
- Полный возврат суммы и комиссии при `FAILED` обязателен и проверяется как успешный сценарий.
- Тексты уведомлений и правила оборота сделать однозначными, убрать требование публиковать полные персональные данные.
- НФТ относятся к 50 новым `POST /transfers` в секунду при стандартной истории 30 000 переводов; служебный опрос статусов и метрик описывается отдельно. Целевые пороги: p95 принятого `POST` ≤ 500 мс; не менее 95% принятых переводов завершаются за ≤ 2 с. Условия и продолжительность подтверждения — в нагрузочном плане. Обязательного прогона на миллионе строк нет.
- Документировать ошибки API, схему таблиц, события и тестовый API. Тестовый API и средства наблюдения работают корректно.

Пороги на целевом ВДИ ещё не подтверждены. Локальные цифры эталона подписываются конкретным окружением; до пилота их нельзя объявлять результатами ВДИ.

## Общий функциональный каталог эталонов

Это группы сценариев для сопоставления глубины решений, а не обязательное число тестовых методов или пунктов будущей шкалы.

| ID | Покрытие |
| --- | --- |
| F01 | Готовность стенда и доступность разрешённых подключений |
| F02 | Перевод `OWN`: завершение, нулевая комиссия, остатки |
| F03 | Перевод `OTHER` в пределах бесплатного порога |
| F04 | Границы и точность суммы: 9,99; 10,00; 300 000,00 для `OWN`; 300 000,01; 10,001 |
| F05 | Отсутствующие поля, неверный формат и неизвестный счёт |
| F06 | Матрица статусов отправителя и получателя |
| F07 | Перевод на тот же счёт отклоняется |
| F08 | Граница дневного лимита: 149 999,99; 150 000,00; 150 000,01 на независимых данных |
| F09 | Сброс дневного лимита при переходе через полночь МСК |
| F10 | Пересечение порога комиссии: 90 000 + 20 000; комиссия 100,00 с превышения |
| F11 | Минимум и округление комиссии после исчерпания порога |
| F12 | Повтор по `Idempotency-Key`: один перевод и одно списание |
| F13 | Тот же ключ с другим телом: 409; новый запрос после 24 часов |
| F14 | `TransferCreated`: связь с запросом, поля; проводки по собственному `transferId` |
| F15 | `PROCESSING` на паузе и завершение после возобновления учёта |
| F16 | `FAILED`: полный возврат суммы и комиссии |
| F17 | Уведомления о `COMPLETED` и `FAILED`: статус, получатель и формат |
| F18 | Оборот учитывает только завершённые переводы выбранной даты |

Для F16 сначала выполнить успешный перевод `OTHER` на 100 000,00, затем перевод на 40 000,00 с комиссией 400,00 при остановленном учёте и закрыть счёт получателя перед возобновлением. Это изолирует проверку полного возврата от проверки пересечения порога. Сравнивать остаток с состоянием непосредственно перед вторым переводом.

Сценарии с часами, остановкой потребителей и оборотом выполняются последовательно на выделенном стенде, возвращают глобальные настройки в `finally`/teardown. Остальные готовят собственных клиентов и счета, не зависят от истории. До полного набора допускается один общий reset; внутри обычных тестов глобальный reset не используется.

## Достоверность четырёх эталонов

- Ожидаемые результаты берутся из ТЗ. Нельзя менять assert на ошибочное фактическое поведение ради зелёного прогона.
- Для Java/Python полный прогон должен быть зелёным: все зарегистрированные проверки проходят, ошибок и пропусков нет. Анализатор сверяет точные testcase ID и отвергает любое failure/error/skip, включая прежние метки KNOWN. Исключений для известных дефектов нет.
- В ручном эталоне есть исполненные кейсы, фактические результаты и доказательства, а не только текст ожидаемых результатов.
- В нагрузочном эталоне есть исходные измерения, достигнутая интенсивность, ошибки, задержка до финального статуса и ограничения интерпретации. Невыполнение НФТ стендом не является ошибкой эталонной методики.
- Эталоны не читают исходники стенда для выполнения тестов, не пишут напрямую в БД и не подменяют JAR. Известные внутренние причины остаются в заметках жюри.
- Проверка упаковки исключает `jury/`, эталоны, исходники стенда, `.m2/`, `target/`, `.venv/` и кэши.
- Проверка из независимого клона с Git LFS подтверждает, что все четыре выдачи содержат настоящие бинарники и запускаются без пересборки или загрузки библиотек.
