# Задания на ревью чужих артефактов

Черновик. Синтетические задания для участников, у которых сейчас нет своих автотестов или тест-кейсов, пригодных для оценки по чек-листу (см. `rating-tasks.md`).

## Идея

Мы сами пишем артефакт и закладываем в него дефекты. Отсюда:

- **ключ известен заранее** — проверка сводится к сверке с ним, экспертиза нужна только при подготовке;
- **дефекты привязаны к пунктам наших чек-листов** — задание проверяет то же, что и оценка собственных артефактов;
- **шкала 0–5, как у собственных артефактов** — баллы сравнимы с участниками, сдавшими свои артефакты. Исключение — 1a и 1d: там 0–100, как их сопоставить, см. открытые вопросы.

## Варианты

### 1a. Код-ревью автотестов — для автоматизаторов

**Статус:** Selenide, Java + SQL и Playwright готовы, см. `1a-autotest-review/`.

- **Даём:** 20 тестов, все равноправны:
  - десять тестов на Selenide в стиле `efr_v2`, общий хелпер и связанные кейсы Test IT. Тесты лежат в Maven-проекте с заглушкой ЕФР, их можно запустить локально;
  - пять тестов на Java + SQL в стиле `at_cft_2` (ЦФТ, РКО ФЛ): классы Criteria, которые собирают SQL для поиска данных, шаги с прямыми запросами к БД и упрощённая схема таблиц. Только чтение;
  - пять тестов на Playwright for Java (JUnit 5) с базовым классом и page object.
- **Заложено:** в каждом тесте ровно 5 дефектов, всего 100, и 10 ловушек — корректного кода, похожего на ошибку. Дефекты Selenide и Playwright — по пунктам чек-листа автотестов и по знанию Playwright (автоожидания, изоляция контекстов, web-first assertions). Половина дефектов Java + SQL — в самом SQL: `NOT IN` с `NULL`, `OR` без скобок, условие LEFT JOIN в `WHERE`, «последняя запись» без `ORDER BY`, синтаксис только для Oracle.
- **Сдаёт:** заполненный шаблон `answer-template.xlsx` — по строке на замечание: тест, строка, что не так, почему, как исправить.
- **Проверка:** +1 за каждый найденный дефект с верной причиной, −2 за каждую ловушку (один раз за ловушку). Итог `max(0, дефекты − 2 × ловушки)`, от 0 до 100. Замечание засчитывается только за тест, который в нём назван. Проверяющий сверяет замечания с ключом по листу подсчёта `scoring-sheet.xlsx`, код открывать не нужно.

Файлы:

- `1a-autotest-review/participant/` — всё, что отдаём участнику: `selenide/`, `sql/` и `playwright/` (песочницы с тестами; в каждой свой `task.md` с заданием и кейсами Test IT) и `answer-template.xlsx` (шаблон ответа). Папку отправляем целиком, архивом;
- `1a-autotest-review/jury/answer-key.md` — ключ, только жюри. Строки ключа сгруппированы по тестам;
- `1a-autotest-review/jury/scoring-sheet.xlsx` — лист подсчёта: 100 строк дефектов и 10 строк ловушек, в каждой 0 или 1, итог считает формула;
- `1a-autotest-review/jury/fixed/` — исправленные версии тестов;
- шаблон ответа и лист подсчёта собираются из ключа скриптом `tools/build_sheets.py`; после правки ключа запустить его заново.

### 1b. Ревью тест-кейсов по требованиям — для ручных тестировщиков

**Статус:** готово, см. `1b-testcase-review/`. Осталось решение 1–2 коллегами.

- **Даём:**
  - три требования в стиле Jira — `BIQ-90101` «Открытие вклада», `BIQ-90102` «Закрытие счёта и вклада», `BIQ-90103` «Создание клиента»;
  - 20 тест-кейсов по ним одной выгрузкой Test IT (`testcases.xlsx`, формат как в реальной выгрузке, плюс колонка «№ шага»).
  Темы взяты из реальных кейсов ЕФР, правила, пороги и тексты сообщений — вымышленные. BIQ — единственный источник истины, знание настоящего ЕФР не помогает.
- **Заложено:** в каждом кейсе ровно 5 дефектов, всего 100, и 10 ловушек — мест, верных по BIQ, но похожих на ошибку.
  - 45 дефектов — расхождения с BIQ: граница, текст сообщения, право роли, лишний или пропущенный контролёр, статус, значение поля.
  - 55 дефектов — по пунктам чек-листа ручных кейсов: неконкретный ожидаемый результат, невоспроизводимый шаг, нет данных или роли, вторая цель, нет техники тест-дизайна.
  - В общих шагах дефектов нет, участнику это сказано.
- **Сдаёт:** заполненный шаблон `answer-template.xlsx` — по строке на замечание: кейс, место («Шаг 3», «Предусловие 1», «Наименование»), что не так, почему, как исправить.
- **Проверка:** как в 1a. +1 за каждый найденный дефект с верной причиной, −2 за каждую ловушку (один раз за ловушку). Итог `max(0, дефекты − 2 × ловушки)`, от 0 до 100. Замечание засчитывается только за кейс, который в нём назван. Проверяющий сверяет замечания с ключом по листу подсчёта `scoring-sheet.xlsx`, выгрузку открывать не нужно.
- **Проверка материала:** решение вслепую нейросетью — 88 из 100 без попаданий в ловушки; исправленные кейсы прочитал отдельный проверяющий. Подробности — в конце ключа.

Файлы:

- `1b-testcase-review/participant/` — всё, что отдаём участнику: `task.md`, `biq/`, `testcases.xlsx`, `answer-template.xlsx`. Папку отправляем целиком, архивом;
- `1b-testcase-review/jury/answer-key.md` — ключ, только жюри. Строки ключа сгруппированы по кейсам;
- `1b-testcase-review/jury/scoring-sheet.xlsx` — лист подсчёта: 100 строк дефектов и 10 строк ловушек;
- `1b-testcase-review/jury/fixed/testcases.xlsx` — исправленные кейсы;
- `1b-testcase-review/jury/source/` — текстовые исходники обеих выгрузок. Кейсы правим только здесь, xlsx собираются скриптами:

  ```bash
  cd review-tasks/tools
  .venv/bin/python build_testcases.py ../1b-testcase-review   # выгрузки участника и исправленная
  .venv/bin/python build_sheets.py ../1b-testcase-review      # шаблон ответа и лист подсчёта
  ```

### 1c. Ревью материалов НТ — для нагрузочников

**Статус:** готово, см. `1c-load-review/`. Осталось решение 1–2 нагрузочниками.

- **Даём:** методику НТ вымышленного бэкенда ЕФР (`methodology.md`) и 20 единиц, подготовленных по ней. Структура как в 1a — 10 + 5 + 5:
  - 10 сценариев JMeter 5.6.3, по одному на операцию профиля: REST с корреляцией, подтверждение контролёром, одноразовые данные, тяжёлая выписка, SOAP в АБС, JDBC-отчёт, подпись запроса в JSR223 на Groovy. Данные — CSV в `scripts/data/`;
  - 5 протоколов НТ в `.docx` по шаблону учебного модуля: поиск максимума, стабильность, сравнение с эталоном, контрольный прогон, hotfix адаптера на заглушке АБС. В каждом таблицы и 2–4 графика в стиле Grafana;
  - 3 дашборда Grafana в JSON (InfluxQL по метрикам JMeter, PromQL по `efr-api`, плагин Zabbix по серверам) и 2 SQL-скрипта для PostgreSQL: подготовка стенда и сбор артефактов после теста.
  Методика — единственный источник истины, числа в протоколах — фактические, запускать ничего не нужно.
- **Заложено:** в каждой единице ровно 5 дефектов, всего 100, и 10 ловушек. 33 дефекта — прямые расхождения с методикой, остальные — по пунктам чек-листа отчёта НТ: достоверность (ошибки с 503 и таймаутами, перегруженный генератор, неподанная нагрузка, прогрев в результатах), критерии, модель нагрузки, условия теста, узкое место и выводы. Ловушки — места, верные по методике: Once Only для входа, хост через `${__P()}`, открытая модель для ОП-08, поиск максимума до 200 %, заглушка АБС с причиной в «Ограничениях», VACUUM FULL ночью.
- **Сдаёт:** заполненный шаблон `answer-template.xlsx` — по строке на замечание: единица, место (путь в дереве JMeter, раздел или таблица протокола, панель дашборда, строка SQL), что не так, почему, как исправить.
- **Проверка:** как в 1a и 1b. +1 за каждый найденный дефект с верной причиной, −2 за каждую ловушку (один раз за ловушку). Итог `max(0, дефекты − 2 × ловушки)`, от 0 до 100. Проверяющий сверяет замечания с ключом по листу подсчёта `scoring-sheet.xlsx`, материалы открывать не нужно. Для протоколов в ключе есть правильный вывод.
- **Проверка материала:** решение вслепую нейросетью — 97 из 100 без попаданий в ловушки; исправленные материалы прочитал отдельный проверяющий, найденное исправлено. Все сценарии загружаются в JMeter 5.6.3. Импорт дашбордов в Grafana не проверялся. Подробности — в конце ключа.

Файлы:

- `1c-load-review/participant/` — всё, что отдаём участнику: `task.md`, `methodology.md`, `scripts/`, `protocols/`, `monitoring/`, `answer-template.xlsx`. Папку отправляем целиком, архивом;
- `1c-load-review/jury/answer-key.md` — ключ, только жюри: дефекты, правильные выводы протоколов, самопроверка чисел, ловушки;
- `1c-load-review/jury/scoring-sheet.xlsx` — лист подсчёта: 100 строк дефектов и 10 строк ловушек;
- `1c-load-review/jury/fixed/` — исправленные сценарии, данные, дашборды и SQL;
- `1c-load-review/jury/source/` — исходники. Материал правим только здесь, файлы участника собираются скриптами:

  ```bash
  cd review-tasks/tools
  .venv/bin/python build_jmx.py ../1c-load-review                                  # сценарии участника и исправленные
  .venv/bin/python ../1c-load-review/jury/source/scripts/make_data.py               # CSV к сценариям
  .venv/bin/python ../1c-load-review/jury/source/monitoring/dashboards.py           # дашборды обеих версий
  .venv/bin/python ../1c-load-review/jury/source/protocols/charts.py 11 12 13 14 15 # графики протоколов
  .venv/bin/python ../1c-load-review/jury/source/protocols/charts.py --check 11 12 13 14 15  # таблицы = числа графиков
  .venv/bin/python build_protocols.py ../1c-load-review                            # протоколы в .docx
  .venv/bin/python build_sheets.py ../1c-load-review                               # шаблон ответа и лист подсчёта
  ```

  SQL-скрипты исправленной версии лежат в `jury/fixed/monitoring/` и правятся вручную.

  Проверка сценариев в настоящем JMeter: скачать `apache-jmeter-5.6.3.tgz` с `archive.apache.org`, указать `JMETER_HOME` и запустить `.venv/bin/python build_jmx.py ../1c-load-review --check`. Скрипт загружает каждый `.jmx` и прогоняет каждый элемент через его окно настроек: так видно, что GUI покажет ровно то, что записано. Нужна Java 17+. Проверка ловит неверное имя или формат свойства, записанного в файле. Не ловит булево свойство со значением false под неверным именем (GUI и так покажет false) и не проверяет, что обязательные свойства заданы.

  `build_sheets.py` для 1c ещё сверяет таблицы протоколов с данными графиков (`charts.py --check`) и проверяет JSON исправленных дашбордов.

### 1d. Код-ревью автотестов на Python — для автоматизаторов

**Статус:** готово. См. `1d-python-review/`.

То же задание, что 1a, для тех, кто пишет автотесты на Python 3.10. Стиль — как в бэкенд-тестах команды СИ: pytest, PyHamcrest, шаги в отчёте, `retrying`.

- **Даём:** 20 тестов, все равноправны:
  - 10 тестов на API сервиса брокерского обслуживания с проверками в БД (SQLite): фикстуры, шаги и класс с SQL-запросами;
  - 5 тестов на Python + Kafka;
  - 5 тестов на Python + Playwright.
- **Заложено:** в каждом тесте ровно 5 дефектов, всего 100, и 10 ловушек. Есть дефекты, характерные именно для Python и pytest: изменяемый аргумент по умолчанию, проверки внутри `pytest.raises`, `xfail` без `strict`, `assert` без сообщения вне тестового модуля. Есть и ошибки в SQL: дата против даты со временем, `date('now')` по UTC, «последняя запись» не своего поручения. В Kafka — последнее сообщение топика вместо своего, проверка дубля до его обработки, отсутствующий топик под видом «сообщений нет».
- **Сдаёт и проверка** — как в 1a: шаблон `answer-template.xlsx`, +1 за дефект, −2 за ловушку, итог от 0 до 100.

Файлы:

- `1d-python-review/participant/python/` — всё, что отдаём участнику: один проект с песочницей и тестами (`tests/api/`, `tests/kafka/`, `tests/ui/`), `task.md` с заданием и кейсами Test IT. Рядом `1d-python-review/participant/answer-template.xlsx` — шаблон ответа. Папку отправляем целиком, архивом, без `.venv` и `build/`;
- `1d-python-review/jury/answer-key.md` — ключ, только жюри;
- `1d-python-review/jury/scoring-sheet.xlsx` — лист подсчёта, как в 1a;
- `1d-python-review/jury/fixed/` — исправленные версии тестов.

## Как устроены папки заданий

В каждом задании две папки:

- `participant/` — самодостаточный комплект для участника, ссылки в `task.md` — относительные внутри этой папки. Ничего жюрийного сюда не кладём.
- `jury/` — ключ и заметки для проверки. В 1b здесь же `source/` — текстовые исходники кейсов, в 1c — исходники сценариев, дашбордов и протоколов.

Архив для отправки собирается из папки задания так, чтобы в него не попали служебные файлы macOS и результаты сборки:

```bash
cd review-tasks/1a-autotest-review/participant && zip -r ../autotest-review.zip . -x '*.DS_Store' '*/target/*' '*/.idea/*' '*/.m2/*' '*/.selenium/*' '*/.allure/*'
cd review-tasks/1d-python-review/participant && zip -r ../python-autotest-review.zip . -x '*.DS_Store' '*/.venv/*' '*/build/*' '*/__pycache__/*' '*/.pytest_cache/*' '*/.idea/*'
cd review-tasks/1b-testcase-review/participant && zip -r ../testcase-review.zip . -x '*.DS_Store'
cd review-tasks/1c-load-review/participant && zip -r ../load-review.zip . -x '*.DS_Store'
```

## Риски

- **Утечка ключа.** Задания выполняют два месяца, рейтинг публикуется еженедельно — ответы могут разойтись между участниками. Варианты защиты:
  - два варианта материала;
  - единый срок сдачи для всех, а не по мере готовности.
- **Нейросети.** Решено не запрещать: участники работают как хотят. Большую часть заложенных дефектов нейросеть находит сразу, поэтому различают участников в основном ловушки — нейросеть склонна помечать подозрительный, но корректный код, а за такие замечания снимается балл.
- **Качество ключа.** Если в материале окажется незапланированный дефект или спорный пункт, баллы станут нечестными. Перед запуском материал решают 1–2 коллеги, не участвующие в конкурсе.
