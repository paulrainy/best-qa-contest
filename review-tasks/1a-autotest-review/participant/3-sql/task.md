# Задание: код-ревью автотестов на Java + SQL

## Что нужно сделать

Коллега написал автотесты на ЦФТ и просит вас проверить их, прежде чем они попадут в общий проект.

1. Откройте папку `src/test/java`. В ней лежат:
   - в `tests/PRODUCTS/R2_DEPOSIT/rko_fl/` — 5 тестов: `OpenCurrentAccountTest.java`, `CashDepositToCurrentAccountTest.java`, `ArrestOnCurrentAccountTest.java`, `CloseCurrentAccountTest.java`, `OpenAccountWithExpiredDocTest.java`;
   - в `model_cft/model/` — `CriteriaClPriv.java` и `CriteriaR2Deposit.java`, классы, которые собирают SQL-запросы для поиска тестовых данных.
2. Каждый тест написан по тест-кейсу из Test IT. Тест-кейсы — в конце этого файла.
3. Найдите всё, что сделано неправильно или плохо, — и в Java-коде, и в SQL.
4. Запишите каждую проблему отдельной строкой в таблицу. Как оформить таблицу — в разделе «Формат ответа».

Тесты написаны на TestNG, отчёт — Allure. Тесты можно запустить — как это сделать, написано в разделе «Как запустить тесты».

Каждый тест устроен одинаково:

1. **Сетап** — поиск тестовых данных в БД.
2. **Авторизация** — вход в ЦФТ под пользователем нужной роли.
3. **Операции** — действия в ЦФТ.
4. **Проверки** — чтение результата из БД.

## Что ещё есть в проекте

Эти классы лежат в `src/main/` вместе с песочницей — маленькой копией ЦФТ, на которой запускаются тесты. Проверять их не нужно. Считайте, что они работают правильно и так, как описано ниже.

**`BasicTest`** — базовый класс тестов:

- `authorization(user)` — вход в ЦФТ под пользователем;
- `getOperDay()` — операционный день пользователя, который вошёл последним;
- `getProductBranchesWithCheckOperDayEqualCurrDay()` — продуктовые филиалы, у которых операционный день совпадает с текущей датой.

**`ParametersBuilderBasic`** — базовый класс для `Criteria*`:

- `queryBuilder` — билдер запроса (см. ниже);
- `getObject()` — первая строка результата или `null`;
- `getRandomObject(n)` — случайный объект из первых `n` строк или `null`. Так в проекте разводят параллельные прогоны по разным данным. Параметры поиска и выбранный объект пишутся в лог и в Allure;
- `addParameter(название, значение)` — подпись условия для лога и Allure, на запрос не влияет.

**`QueryBuilder`** собирает `SELECT`:

- `select`, `from` и `join(String)` добавляют текст в соответствующие части запроса;
- `join(QueryBuilder)` переносит в запрос JOIN и условия WHERE другого билдера;
- `where(String)` добавляет условие. Условия соединяются через `AND`, каждое берётся в скобки;
- ограничение числа строк билдер добавляет сам, в синтаксисе СУБД стенда. Текст JOIN и условий уходит в БД как есть.

**`DaoCommon`** выполняет запрос как есть, `:имя` — bind-переменная из переданной `Map`. Только на стендах PostgreSQL он берёт в кавычки имена таблиц с `#`: иначе PostgreSQL читает `#` как оператор.

- `selectOne(sql, класс, параметры)` — первая строка или `null`;
- `selectValue(sql, класс, параметры)` — одно значение;
- `executeUpdate(sql, параметры)` — выполняет запрос и фиксирует изменения (commit).

**`CriteriaUser.findUser()`** — случайный пользователь из подразделения с нужной ролью или `null`.

**Хелперы операций** (`OpenNewDepositPageHelper`, `ContractSignPageHelper`, `IncomingCashPageHelper`, `ReceiptDocumentByCashierPageHelper`, `AddBlockPageHelper`, `CloseContractPageHelper`) выполняют операции ЦФТ так, как называются их методы:

- `clickOk()` нажимает «ОК» и падает, если ЦФТ вернул ошибку;
- `clickOk(true)` — для негативных тестов, ошибку не проверяет;
- `getObject()` возвращает созданный договор из БД.

**Сущности** `Dto_Deposit`, `DtoClPriv`, `DtoR2FactOper`, `Dto_User` отображают строки таблиц:

- `update()` перечитывает объект из БД;
- `getBalance()` возвращает остаток на счёте договора.

**Проверки `AssertionsUtil.assertThat(...)`:**

- `hasStateEqual(состояние)` перечитывает объект из БД, пока состояние не станет ожидаемым. Таймаут по умолчанию — 60 секунд, другой можно передать вторым параметром;
- `objectExist()` / `objectNotExist()` — объект найден / не найден;
- `hasBalanceEqualTo`, `hasDateCloseEqualTo`, `hasAccountStartWith` — остаток, дата закрытия и номер счёта договора;
- `whereR2AnnAccount` — проверки счёта договора, `whereMainDocum` — проверки документа операции.

## Стенды и БД

Стенды ЦФТ бывают на Oracle и на PostgreSQL, схема БД и имена таблиц на них одинаковые. Если тест предназначен для стендов одного типа, это указано в комментарии над тестовым методом.

Таблицы, которые используются в тестах (упрощённо). Колонки `C_DATE_*` хранят дату без времени.

| Таблица | Что хранит | Колонки |
| --- | --- | --- |
| `Z#CLIENT` | Клиенты | `ID`; `C_NAME` — ФИО; `C_FILIAL` — код филиала; `C_IS_RESIDENT` — `'1'` резидент, `'0'` нет |
| `Z#CL_PRIV` | Клиенты — физические лица | `ID` = `Z#CLIENT.ID`; `C_DOC_DATE_END` — дата окончания срока действия ДУЛ; `C_DEATH_DATE` — дата смерти |
| `Z#CL_BLOCK` | Действующие блокировки клиента. Снятые блокировки переносятся в архив | `ID`; `C_CLIENT` → `Z#CL_PRIV.ID` |
| `Z#EXECUTORY_PROCESS` | Исполнительные производства | `ID`; `C_CLIENT` → `Z#CL_PRIV.ID` — должник; пусто, пока производство не сопоставлено с клиентом банка |
| `Z#SHB_FORMA_CRS` | Формы CRS | `ID`; `C_CLIENT`; `C_CRS_STATUS` — статус |
| `Z#SHB_FORMA_FATCA` | Формы FATCA | `ID`; `C_CLIENT`; `C_DATE_END` — дата окончания действия формы, пусто — бессрочная |
| `Z#R2_DEPOSIT` | Договоры «Розница. Депозиты», в том числе текущие счета | `ID`; `C_NUM_DOG` — номер; `C_CLIENT` → `Z#CL_PRIV.ID`; `C_COM_STATUS` → `Z#COM_STATUS_PRD.ID`; `C_CURRENCY` — код валюты; `C_FIN_PRODUCT` — код финансового продукта; `C_FILIAL`; `C_DEPART`; `C_ACCOUNT` → `Z#AC_FIN.ID`; `C_DATE_CREATE`; `C_DATE_CLOSE` |
| `Z#COM_STATUS_PRD` | Справочник состояний договоров и счетов | `ID` — суррогатный ключ, генерируется последовательностью при заполнении справочника на стенде; `C_CODE` — код: `WAIT_CONF`, `WORK`, `OPEN`, `CLOSE`; `C_NAME` — название |
| `Z#AC_FIN` | Лицевые счета | `ID`; `C_MAIN_V_ID` — номер счёта; `C_SALDO` — остаток; `C_COM_STATUS` → `Z#COM_STATUS_PRD.ID` |
| `Z#R2_DEP_HOLD` | Блокировки сумм по договору | `ID`; `C_DEPOSIT` → `Z#R2_DEPOSIT.ID`; `C_KIND` — вид: `ARREST`, `BLOCK`; `C_SUM`; `C_STATE` — `ACTIVE` или `CLOSED`; `C_DATE_BEGIN` |
| `Z#R2_IP_CARDS` | Карты к договору | `ID`; `C_DEPOSIT` → `Z#R2_DEPOSIT.ID`; `C_STATE` — `ACTIVE` или `CLOSED` |
| `Z#R2_FACT_OPER` | Фактические операции по договору | `ID`; `C_DEPOSIT` → `Z#R2_DEPOSIT.ID`; `C_SUM`; `C_STATE`; `C_DATE`; `C_MAIN_DOCUM` — документ |

| Тест | Файл:строка | Замечание |

В колонке «Замечание» напишите, что не так и почему это проблема. Исправление предлагать не обязательно, но верное исправление тоже показывает, что вы поняли причину.

## Как считаются баллы

- Задание — это 20 тестов: 10 на Selenide, 5 на Playwright и 5 на SQL. Все равноправны. Песочницы пронумерованы: `1-selenide`, `2-playwright`, `3-sql`, в таком же порядке тесты идут в `answer-template.xlsx`.
- В каждом тесте ровно 5 дефектов. За каждый найденный дефект с верной причиной — 1 балл, максимум 100.
- В тестах и общем коде есть ловушки — места, которые выглядят подозрительно, но написаны правильно. За каждое замечание, которое называет ошибкой правильный код, снимается 2 балла.

## Как запустить тесты

### Что нужно установить

- **Java 17** или новее. Проверить: `java -version`.
- **Maven 3.6.3** или новее. Проверить: `mvn -v`.

Больше ничего не нужно: ни стенд, ни СУБД, ни браузер. Песочница — API ЦФТ и базы данных стендов — запускается сама вместе с тестами. Базы данных работают на H2: это библиотека Java, Maven скачает её сам. Всё скачанное остаётся в этой папке, в `.m2`.

### Стенды песочницы

| Стенд | СУБД | Как запустить тесты на нём |
| --- | --- | --- |
| RTEST | Oracle | `mvn test` — это стенд по умолчанию |
| INTEST | Oracle | `mvn test -Dstand=INTEST` |
| PGRF1RT | PostgreSQL | `mvn test -Dstand=PGRF1RT` |

Базы стендов работают на H2 в режиме совместимости с Oracle или PostgreSQL. Режим совместимости близок к настоящим СУБД, но повторяет их не во всём. Если сомневаетесь, как поведёт себя запрос, ориентируйтесь на документацию Oracle и PostgreSQL.

На стендах заранее есть пользователи, клиенты, договоры, карты, блокировки и операции — как на живом стенде. Данные заполняются заново при каждом запуске.

### Запуск из терминала

1. Откройте терминал в этой папке — там, где лежит `pom.xml`.
2. Запустите все тесты:

   ```bash
   mvn test
   ```

3. В конце Maven напишет, сколько тестов прошло и сколько упало. Полный прогон идёт 1–2 минуты.

Другие варианты запуска:

| Что нужно | Команда |
| --- | --- |
| Запустить один тест | `mvn test -Dtest=OpenCurrentAccountTest` |
| Запустить на другом стенде | `mvn test -Dstand=PGRF1RT` |
| Открыть отчёт Allure после прогона | `mvn allure:serve` |

В PowerShell параметры с точкой берите в кавычки, например `mvn test "-Dcft.port=18091"`.

В Git Bash на Windows русский текст в консоли выводится кракозябрами. Один раз выполните в Git Bash:

```bash
echo 'export MAVEN_OPTS="$MAVEN_OPTS -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8 -Dsun.stdout.encoding=UTF-8 -Dsun.stderr.encoding=UTF-8"' >> ~/.mavenrc
```

Maven читает этот файл при каждом запуске из Git Bash, больше ничего делать не нужно. В PowerShell, cmd и IntelliJ IDEA настройка не нужна и не действует.

### Запуск из IntelliJ IDEA

1. File → Open → выберите эту папку. IDEA сама поймёт, что это Maven-проект.
2. Чтобы IDEA тоже качала библиотеки в папку проекта, откройте Settings → Build, Execution, Deployment → Build Tools → Maven. В поле **Local repository** поставьте галочку **Override** и укажите папку `.m2/repository` внутри этой папки. Потом нажмите справа на панели Maven кнопку обновления (Reload All Maven Projects).
3. Откройте любой тест, например `OpenCurrentAccountTest`, и нажмите зелёную стрелку рядом с именем класса.
4. Все тесты сразу: правой кнопкой по `src/test/resources/testng.xml` → Run.
5. Другой стенд: в настройках запуска (Run → Edit Configurations) добавьте в VM options `-Dstand=PGRF1RT`.

### Где смотреть результат

- **Вывод в консоли** — какие тесты прошли и с какой ошибкой упали остальные. Там же для каждого поиска тестовых данных: параметры, текст SQL-запроса и выбранный объект.
- **Отчёт Allure** (`mvn allure:serve`) — шаги каждого теста, тексты SQL-запросов и их результаты.

### Посмотреть песочницу своими руками

Можно запустить песочницу отдельно и выполнять свои запросы к базам стендов:

```bash
mvn exec:java
```

Откройте консоль базы данных http://localhost:18082. В поле **JDBC URL** укажите адрес стенда, **User Name** — `sa`, пароль оставьте пустым, нажмите **Connect**.

| Стенд | JDBC URL |
| --- | --- |
| RTEST | `jdbc:h2:tcp://localhost:19092/mem:RTEST;MODE=Oracle` |
| INTEST | `jdbc:h2:tcp://localhost:19092/mem:INTEST;MODE=Oracle` |
| PGRF1RT | `jdbc:h2:tcp://localhost:19092/mem:PGRF1RT;MODE=PostgreSQL` |

Пока песочница запущена, тесты работают с ней и свою не поднимают — изменения, сделанные в консоли, видны тестам. Остановить — Ctrl+C в терминале, после перезапуска данные будут как в начале.

Операции ЦФТ тесты выполняют через API песочницы, `http://localhost:18090/cft/<стенд>/api/`. Как его вызывать, видно в хелперах операций в `src/main/java/CFT/`. Пароль всех пользователей ЦФТ в песочнице — `Cft#Playground`.

### Можно ли что-то менять

Да. Запускайте тесты в любом порядке и на любом стенде, правьте их, меняйте данные стендов через консоль, правьте песочницу в `src/main/`. Сдавать изменённый код не нужно: оценивается только таблица замечаний.

### Если не запускается

| Что видно | Что делать |
| --- | --- |
| `mvn: command not found` или `java: command not found` | Не установлен Maven или Java, либо их нет в `PATH`. |
| Папка `.m2` с библиотеками появилась не в песочнице, а в другой папке | `mvn` запущен не из папки песочницы. Перейдите в папку, где лежит `pom.xml`, и запустите снова. |
| Maven не может скачать библиотеки | Нет доступа к Maven Central. Возьмите рабочий `settings.xml` с корпоративным зеркалом. |
| Ошибки про занятый порт или все тесты сразу падают с ошибкой API | Порт 18090, 19092 или 18082 занят другой программой. Закройте её или укажите другие порты: `-Dcft.port=18091`, `-Dcft.db.port=19093`, `-Dcft.console.port=18083`. В адресах JDBC тогда поменяйте порт тоже. |
| В Git Bash вместо русского текста кракозябры | Настройте кодировку вывода, см. «Запуск из терминала». На работу тестов это не влияет. |
