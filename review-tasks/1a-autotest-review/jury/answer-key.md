# Ключ: код-ревью автотестов (задание 1a)

**Только для жюри, участникам не отправлять.**

Задание — 20 тестов в трёх песочницах: 10 на Selenide (TK900101–TK900110), 5 на Java + SQL (TK900116–TK900120), 5 на Playwright (TK900111–TK900115). Все тесты равноправны, части названы только для навигации. В каждом тесте ровно 5 дефектов, все в файле самого теста — всего 100. Ловушек 10, они лежат и в тестах, и в общем коде.

Исправленные версии тестов — в `jury/fixed/`, участникам не отправляются.

## Как считаем

- +1 за каждый дефект из ключа, найденный с верной причиной. Пункт чек-листа называть не обязательно, важно понять, что именно не так.
- Тест обязательно назван: замечание засчитывается только за тест, который в нём указан. «Везде sleep» без тестов не засчитывается.
- Если дефект в одном тесте ломает другой тест, замечание засчитываем у любого из двух — в колонке «Засчитываем, если…» это сказано. Считается такой дефект один раз.
- −2 за каждую ловушку, в которую попал участник. Попадание — участник считает место ошибкой и предлагает его исправить. Если он отметил место как подозрительное и сам объяснил, почему оно корректно, штрафа нет. Каждая ловушка штрафуется один раз, сколько бы раз её ни упомянули. Штраф снимается с общей суммы.
- Итог: `max(0, дефекты − 2 × ловушки)`, от 0 до 100.
- Замечания, которых нет в ключе, баллов не дают и не штрафуются. Спорные разбираем с Мариной Каприз.

Лист подсчёта — `jury/scoring-sheet.xlsx`: 100 строк дефектов и 10 строк ловушек, в каждой ставим 0 или 1, итог считает формула. Как проверять: для каждого замечания участника открыть в ключе все 5 строк названного теста и найти ту, с которой замечание совпадает по смыслу — сверять с колонкой «Засчитываем, если…». Номер строки нужен только чтобы быстрее найти нужную строку ключа: если участник указал строку неточно, но по смыслу замечание совпадает, засчитываем. Если участник описал симптом при запуске (падение на другой строке, файл в build/traces и т. п.), засчитываем там, где в колонке «Засчитываем, если…» это прямо сказано. Код открывать не нужно.

Шаблон ответа участника — `participant/answer-template.xlsx`. Оба файла собираются из этого ключа скриптом `review-tasks/tools/build_sheets.py`: после правки ключа запустить его заново.

## Пункты чек-листа и технические категории

Каждый дефект относится к пункту чек-листа автотестов из `rating-tasks.md` или к технической категории. Пять дефектов теста не обязаны покрывать все пункты.

| Пункт | Что проверяем |
| --- | --- |
| 1 ⛔ | Ожидаемые результаты кейса покрыты проверкой |
| 2 | Нет жёстких пауз: ждём по условию, а не фиксированное время |
| 3 | Нет зашитых стендов, адресов, учёток и паролей |
| 4 | Тест не зависит от других тестов и от порядка запуска |
| 5 | При падении понятно, что сломалось |
| SQL | Запрос выбирает те данные, которые нужны тесту, и работает на всех стендах |
| Playwright | Локаторы, автоожидание и действия Playwright используются как задумано |

## Верные замечания вне ключа

Верные, но не заложенные специально. Баллов не дают, не штрафуются.

**Selenide**

- В TK900102 вводится `50000`, а сравнивается с `50 000` — зависит от форматирования поля.
- В TK900102 проверка стоит прямо в тесте и обращается к xpath страницы в обход хелпера, хотя остальные проверки в проекте живут в хелперах. Это стиль проекта, а не пункт чек-листа.
- В TK900106 `setCashLimit` сам открывает вкладку «Лимиты», поэтому `openTab` перед ним лишний. За Д106.2 это замечание не засчитываем.
- В TK900107 `getText()` не ждёт вообще, так что глобальный таймаут не решает заявленную проблему. У проверки номера карты на строке 56 нет подписи — верно, но Д107.3 засчитываем только за то, что номер сверяется не целиком.
- Повторяющийся во всех тестах код входа в ЕФР — стилистика.
- В TK900108 проверка внутри `try` ждёт сообщения весь таймаут Selenide — тест медленнее, чем мог бы быть.
- В TK900109 оба прогона называются в Allure одинаково. Allure показывает параметры, но в названии значение не видно.

**Java + SQL**

- Значения подставляются в SQL через `formatted`, а не bind-переменными. Для enum и `LocalDate` инъекции нет. Замечание про переиспользование плана запроса и единообразие с приватными методами тестов, где используются bind-переменные, разумное.
- На настоящем PostgreSQL `Z#…` без кавычек — синтаксическая ошибка: `#` там оператор. В песочнице `DaoCommon` берёт такие имена в кавычки сам, в `at_cft_2` это делает `QueryBuilder`, а текст своих фрагментов и запросов в тестах уходит как есть. Участник из команды ЦФТ может это заметить.
- В TK900116, TK900117, TK900119, TK900120 тест дописывает условия в билдер через `getQueryBuilder().where(...)` или `join(...)`, а не методом Criteria: эти условия не попадают в подпись поиска в логе и Allure. Сами ошибки в этих фрагментах — отдельные дефекты, замечание про стиль баллов не даёт.
- В TK900118 доступный остаток считается по блокировкам с датой начала не позже сегодняшней, а не операционного дня. На стендах, где они совпадают, это не влияет.
- В TK900118 у проверки числа блокировок (строки 58–59) нет подписи. Если участник написал только это, Д118.4 не засчитываем.

**Playwright**

- Статические `playwright` и `browser` сломаются, если запускать классы параллельно в одной JVM: каждый класс перезапишет общие поля. Для последовательного запуска всё верно. Это не попадание в Л8: участник говорит о параллельном запуске, а не о том, что тесты делят состояние сейчас.
- Трейс сохраняется для каждого теста, а не только для упавших. Место на диске, но не дефект.
- В TK900115 проверка кода ответа дублирует проверки интерфейса после неё.
- В TK900115 заголовок окна проверяется по части текста (строка 34). Это не дефект: в окне кроме заголовка есть кнопки, точное совпадение здесь не подходит. Участники могут отметить это место по аналогии с Д115.1 — баллов не даём, не штрафуем.
- В `CardPage.open` регулярное выражение «последние цифры в конце» найдёт ссылку и на другую карту клиента с теми же последними цифрами. В песочнице у одного клиента таких карт не бывает.
- В TK900114 приватный метод `isCardNumberMasked` без `@Step`: в Allure проверка маски не видна отдельным шагом. Сам метод — часть Д114.2 и Д114.5.
- В TK900114 локатор номера карты собран заново, хотя в `CardPage` для этого есть `requisite(...)` — дублирование описания страницы.

## Что проверить перед запуском

- После любой правки тестов пересобрать ключ: номера строк в нём точные. Из корня репозитория: `cd review-tasks/tools && .venv/bin/python build_sheets.py ../1a-autotest-review --show` печатает строки кода, на которые ссылается ключ, — у каждого дефекта в строке должна быть заложенная ошибка, у каждой ловушки — корректный код. Затем `cd review-tasks/tools && .venv/bin/python build_sheets.py ../1a-autotest-review` пересобирает шаблон ответа и лист подсчёта.
- Прогнать песочницы на ВДИ (Яндекс Браузер, Maven 3.6.3) и сверить результат с разделом «Что видно в песочнице».
- Java + SQL-часть запускается на H2 2.5 в режимах Oracle и PostgreSQL. Перед запуском стоит повторить запросы Д116.3, Д116.4, Д119.5 и ловушки Л6 на настоящих Oracle и PostgreSQL, а для Д118.5 убедиться, что на PostgreSQL-стенде нет совместимости с `NVL`, например расширения orafce.
- Имена методов хелперов и проверок в SQL-части придуманы по образцу `at_cft_2`. Если участники из команды ЦФТ знают настоящие, расхождение может их сбить — сверить с проектом.
- Дать решить задание одному-двум коллегам, не участвующим в конкурсе. Если они находят меньше трети дефектов или спотыкаются о формулировку, упростить.
