# Ключ: ревью материалов нагрузочного тестирования (задание 1г)

**Только для жюри, участникам не отправлять.**

Задание — методика НТ ЕФР (`participant/methodology.md`) и 20 единиц, подготовленных по ней:

- 01–10 — сценарии JMeter 5.6.3, по одному на операцию профиля ОП-01–ОП-10 (`participant/scripts/`);
- 11–15 — протоколы НТ (`participant/protocols/`);
- 16–18 — дашборды Grafana (`participant/monitoring/*.json`);
- 19–20 — SQL-скрипты подготовки стенда и сбора артефактов (`participant/monitoring/*.sql`).

Все единицы равноправны. В каждой ровно 5 дефектов, всего 100. Ловушек 10. В методике дефектов нет.

Исправленные сценарии, дашборды и SQL — в `jury/fixed/`, участникам не отправляются. Для протоколов исправленного документа нет: правильный вывод по каждому — в разделе «Протоколы: правильный вывод». Исходники сценариев и протоколов — `jury/source/`.

## Как считаем

- +1 за каждый дефект из ключа, найденный с верной причиной. Номер правила методики или пункт чек-листа называть не обязательно, важно понять, что именно не так.
- Единица обязательно названа. Замечание засчитывается только за единицу, которая в нём указана: «во всех скриптах нет таймаутов» без номеров единиц не засчитывается.
- Место нужно только для того, чтобы быстрее найти строку ключа. Если участник указал место неточно (соседний элемент дерева, другой запрос той же панели, соседняя строка SQL), но по смыслу замечание совпадает, засчитываем.
- −2 за каждую ловушку, в которую попал участник. Попадание — участник считает место ошибкой и предлагает его исправить. Если он отметил место как подозрительное и сам объяснил, почему оно верно, штрафа нет. Каждая ловушка штрафуется один раз, сколько бы раз её ни упомянули. Штраф снимается с общей суммы.
- Итог: `max(0, дефекты − 2 × ловушки)`, от 0 до 100.
- Замечания, которых нет в ключе, баллов не дают и не штрафуются. Замечания к методике не оцениваются.

Лист подсчёта — `jury/scoring-sheet.xlsx`: 100 строк дефектов и 10 строк ловушек, в каждой ставим 0 или 1, итог считает формула.

Как проверять:

1. Для каждого замечания участника открыть в ключе все 5 строк названной единицы.
2. Найти строку, с которой замечание совпадает по смыслу, сверяя с колонкой «Засчитываем, если…».
3. Открывать сценарии, протоколы и дашборды не нужно.

Шаблон ответа участника — `participant/answer-template.xlsx`. Оба файла собираются из этого ключа скриптом `review-tasks/tools/build_sheets.py`. После правки ключа его нужно запустить заново.

## Категории

Каждый дефект относится к правилу методики или к пункту чек-листа отчёта НТ из `rating-tasks.md`. Пять дефектов единицы не обязаны покрывать все категории.

| Категория | Что проверяем |
| --- | --- |
| М | Расхождение с методикой: не то значение, не тот способ, нарушено правило с номером |
| 1 ⛔ | Результаты достоверны: ошибки, включая 503 и таймауты, считаются отдельно; генератор не был узким местом; целевая нагрузка фактически подана; прогрев исключён; скрипт проверяет ответы |
| 2 | Критерии успеха измеримы: интенсивность, перцентиль времени отклика по операциям, доля ошибок; итог сравнивается с ними |
| 3 | Профиль и модель нагрузки обоснованы: доли и интенсивность по профилю, модель держит заданную интенсивность |
| 4 | Условия теста сопоставимы с продом или отличия указаны: объём данных, тестовые пользователи, заглушки, длительность |
| 5 | Узкое место и выводы подтверждены метриками: ограничивающий ресурс назван со ссылкой на метрику, рекомендации следуют из данных |
