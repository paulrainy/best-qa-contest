# Автотесты RTF: выжимка

Выжимка по папке «…_RTF» из `help-docs`. В ней фрагменты Java-проекта команды RTF: API-тест рабочего места дилера (блоттер заявок) и классы шагов к нему. Фреймворк команды (`ru.origami.*`) и модели в папку не входят, поэтому код не собирается.

## Состав

| Файл | Что это |
|---|---|
| `PatchDealRequestsConfirm.java` | Тестовый класс: `PATCH /api/v1/deal-requests/confirm` |
| `DatabaseSteps.java` | Шаги с БД: чтение заявки через HQL, вставка заявки нативным SQL |
| `BlotterSteps.java` | Проверка записи о ручной обработке заявки |
| `BlotterWsSteps.java` | Подключение к WebSocket и проверка сообщений |
| `KafkaConsumerSteps.java` | Настройка Kafka-консьюмера из конфигурации стенда |
| `ТК 526914 (1).xlsx` | Тест-кейс СОФР «Еженедельный отчёт по сделкам РЕПО», побайтно совпадает с файлом из папки СОФР. К коду RTF отношения не имеет, видимо, приложен по ошибке. Разбор — в [../sofr-autotests/README.md](../sofr-autotests/README.md) |

## Тест `successPatchDealRequestsWithAllSystemOrigin`

**Стек:** Java, JUnit 5 (параметризованные тесты), REST Assured, Hibernate (PostgreSQL), Kafka, WebSocket. Отчёт в Allure и Test IT через внутренний фреймворк `origami`.

**Сценарий:** тест запускается по разу на каждую систему-источник из `ESystemOrigin`.

1. **Подготовка.** Перед тестом в Kafka публикуются рыночные котировки EUR/RUB и XAU/RUB.
2. **Подписка.** Тест подписывается на топик WebSocket и на топик Kafka.
3. **Данные.** В БД вставляется заявка типа Limit order, её курс сдвигается от рыночного на 2%.
4. **Вызов API.** Под пользователем-дилером вызывается `PATCH …/confirm` со статусом `RATE_CONFIRMED`.
5. **Проверки:**
   - код и тело ответа;
   - сообщение в Kafka-топике заявок;
   - сообщение в WebSocket со статусом заявки.
6. **Очистка.** После теста котировки удаляются из топика, процент допустимого отклонения в БД возвращается к 5,00, подписка на WebSocket снимается.

**Что сделано хорошо:**

- адреса, порты и учётные данные БД, Kafka и WebSocket берутся из конфигурации стенда (`Environment.get`), в коде их нет;
- проверки собраны в `assertAll` и подписаны именем поля, поэтому при падении видно все расхождения сразу;
- WebSocket-сообщение ищется по id заявки, а не берётся первое попавшееся;
- в классе есть ссылки на документацию методов в Confluence;
- после теста топик и БД возвращаются в исходное состояние.

**Замечания:**

- **Два способа подставить параметры в одном классе.** В `getLastDealRequestById` параметры подставлены в HQL как текст (`':id'` и `changeParameter`), а в соседнем `getDealRequestById` — через `setParameter`. Первый способ уязвим для подстановки чужого текста и ломается на кавычке в значении. В `insertDealRequest` так же через текст собран целый блок `DO $$ … $$` с тремя `INSERT`.
- **Название шага не соответствует запросу.** Шаг `getDealRequestById` называется «Получаем последнюю созданную заявку», но запрос без `ORDER BY`, а `setMaxResults(1)` при поиске по id не нужен.
- **Случайные данные без фиксации.** Сторона сделки, клиент, тип операции и наличие комментария выбираются случайно. При падении нельзя повторить тот же набор, если значения не попали в отчёт.
- **Пауза.** В `@BeforeEach` стоит `waitInMillis(1000)` — ожидание, пока котировки дойдут до сервиса.
- **Тест включён только на локальном стенде.** Условие `@EnabledIfSystemProperty(named = "stand", matches = "local.*")` выключает тест в общих прогонах, и он молча пропускается без пометки в отчёте.
- **Глобальная настройка восстанавливается вслепую.** `@AfterEach` записывает в БД процент отклонения 5,00, хотя тест его не меняет. Если на стенде настроено другое значение, тест его перезапишет. При параллельном запуске тесты, которые меняют этот процент, будут мешать друг другу.
- **Заявка не удаляется.** Вставленная в БД заявка остаётся на стенде после теста.
- **Из Kafka берётся первое сообщение** (`dealResponseMessages.get(0)`) без проверки, что оно одно.
- **Неиспользуемый код.** В блоке `DO $$` объявлены переменные `NEW_LO` и `max_num`, которые нигде не используются.
- **Противоречивые настройки Kafka.** Протокол — `PLAINTEXT`, но рядом настраивается truststore для SSL.

## Что полезно для конкурса

- **Второй образец Java-стиля, кроме efr_v2 и at_cft_2.** Это JUnit 5 + REST Assured + Kafka + WebSocket, API-тест без UI. Подходит для задания 1а, если нужно разнообразить стек или добавить вариант для бэкенд-автоматизаторов.
- **Готовые дефекты:**
  - параметры подставлены в HQL текстом рядом с правильным `setParameter`;
  - пауза в `@BeforeEach`;
  - тест молча выключен на общих стендах;
  - восстановление глобальной настройки константой;
  - данные не удаляются после теста.
- **Готовые ловушки:**
  - `assertAll` с подписями полей;
  - очистка Kafka-топика в `@AfterEach`;
  - поля класса в JUnit 5 — экземпляр класса создаётся на каждый тест, поэтому общего состояния между запусками нет;
  - конфигурация через `Environment.get`.
