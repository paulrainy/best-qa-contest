## Тест 1. Заказ справки НДФЛ в мобильном приложении

**Кейс:** Test IT 1032714, `test_ndfl_order_and_download_kafka`, регресс, интеграционный E2E.

**Сценарий:** в приложении на Android пользователь заказывает справку НДФЛ за текущий год. Тест проверяет экраны, запись в PostgreSQL (`cs_reporting.tax_report`) и сообщение в Kafka (топик `sofr.get-tax-report-info-request`). Kafka читается не напрямую, а через HTTP-шлюз QA Service.

**Стек:** pytest, PyHamcrest, Allure и Test IT (через обёртку `titallure`), Appium-обёртка команды, `requests`, `pg8000`.

| Файл | Что внутри |
|---|---|
| `test_kafka_reports.py` | Тест: шаги в `titallure.step`, проверки `assert_that` с сообщениями |
| `screens_more.py` | Локаторы экранов по `resource-id` и тексту, у каждого — описание для отчёта |
| `actions_more.py` | Ожидание сообщения в Kafka: опрос QA Service до таймаута |
| `db_client.py` | `BrokerDB.get_last_ndfl_report` — последняя за сегодня запись НДФЛ клиента, параметр через `%s` |
| `qa_service.py` | HTTP-клиент QA Service для чтения топика |
| `conftest.py` | Фикстуры: БД с запасным подключением через QA Service, телефон с пользователем из группы `xdist_group` и сбросом его состояния |

**Что сделано хорошо:**

- локаторы, шаги и доступ к БД и Kafka разнесены по слоям;
- у каждой проверки есть сообщение;
- пользователь берётся из пула по группе xdist и сбрасывается перед тестом, включая уже заказанные справки (`clean_tax_report=True`);
- SQL с bind-параметром, сортировка «последней записи» задана явно.

**Замечания по коду:**

- **Название обещает больше, чем проверяется.** Тест и кейс называются «заказ и скачивание справки», но шага скачивания в тесте нет.
- **Сообщение в Kafka не привязано к клиенту.** Из сообщений за день берётся ближайшее по времени, и сверяется только `TaxPeriod`. Справка, которую в это же время заказал другой пользователь или параллельный прогон, тоже пройдёт проверку.
- **Ожидание в Kafka прерывается не там.** Пустой ответ опрашивается повторно, а если сообщение есть, но не то (не тот период, вне текущего дня), тест падает сразу, не дожидаясь нужного.
- **Часовой пояс.** `RequestTime` считается временем в UTC, «текущий день» тоже берётся в UTC. Если сервис пишет московское время, с 00:00 до 03:00 по Москве проверка ломается.
- **Ошибка настройки маскируется под отсутствие сообщения.** Если топика нет в кластере, `kafka_subscribe` возвращает `{}`, и тест до таймаута пишет «сообщений нет».
- **Отладка через `print`,** а не через лог или Allure.
- **Текущий год из `datetime.now()`.** Тест зависит от даты запуска: в новогоднюю ночь ожидаемый год может разойтись с годом в приложении.

## Тест 2. Создание клиента через Kafka

**Кейс:** Test IT 540318, `test_200_create_client`, smoke.

**Сценарий:** тест собирает большой JSON с данными клиента — ФИО, паспорт, адреса, телефоны, договоры, тарифы, торговые площадки и счета — и отправляет его в Kafka. Затем проверяет, что Broker 2 сохранил клиента в БД и что клиент может войти через API. После теста клиент удаляется.

**Стек:** pytest, PyHamcrest, `retrying`, внутренние библиотеки `rshbrestclient` и `rshbdatabase`, отчёт через `Reporting` (Allure и Test IT).

| Файл | Что внутри |
|---|---|
| `test_1_create_client.py` | Тест: сборка запроса по шагам, отправка в Kafka, проверки БД и авторизации |
| `create_req_kafka.py` | Builder `SiClientInfo` (583 строки): по методу `add_*` на каждый блок запроса, случайные ФИО, паспорт, телефоны |
| `b2_broker.py` | Базовый класс доступа к БД: общий кеш подключений, запасной путь через QA Service, разбор дат в ответе, декоратор `fetch_one` |
| `b2_client_info.py` | Поиск клиента по логину с повтором до 45 секунд |
| `client.py` | API-клиент auth-service: модели запросов и ответов, шифрование телефона и кода, декоратор `swag_coverage` для учёта покрытия API |
| `conftest.py` | Фикстуры: уникальный логин с удалением клиента после теста, подключения к БД и QA Service |

**Что сделано хорошо:**

- тестовые данные собираются Builder'ом, тест читается как бизнес-сценарий;
- данные уникальные, после теста клиент удаляется;
- ожидание записи в БД — повтор с таймаутом, а не пауза;
- в API-клиенте учитывается покрытие методов Swagger.

**Замечания по коду:**

- **SQL собирается f-строкой:** `WHERE c.login = '{login}'` в `b2_client_info.py`.
- **Проверки обращаются к спискам как к словарям.** В `PhoneList.Phone`, `EmailList.Email` и `IdentityDocumentList.IdentityDocument` Builder кладёт списки, а тест берёт из них `['PhoneNumber']`, `['EmailAddress']` и `['DocumentNumber']`. В шаге авторизации тот же телефон взят уже по индексу `[3]`. В таком виде тест упадёт с `TypeError` на первой же проверке телефона.
- **В тесте не хватает импортов** (`V2LoginQuestRq`, `HeadersAuth`, `Broker2Api` и других), в `conftest.py` нет фикстуры `b2_client_info`. Похоже, код вырезан из проекта для примера.
- **Название шага не соответствует действию.** В шаге «Удалить ранее созданного клиента» логин только присваивается, а удаление происходит в финализаторе после теста.
- **Логин — 7 случайных цифр,** без проверки, что такого клиента ещё нет.
- **Даты в запросе зашиты:** `RequestTime` 2024-11-20, даты выдачи и окончания паспорта, `BindDate`.
- **Ошибки в Builder:**
  - `del_list` удаляет из списка последний элемент (`path.pop()`), а не найденный, и делает это прямо во время обхода списка;
  - `_round_for_depo_account_info_list` объявлен в классе дважды, второе объявление молча заменяет первое.
- **`send_query` удаляет переводы строк из запроса** перед отправкой через QA Service. Комментарий `--` внутри SQL после этого закомментирует весь остаток запроса.

## Что полезно для конкурса

- **Образец стиля для задания 1д (ревью автотестов на Python).** Это реальный код команды: pytest + PyHamcrest, шаги в контекстных менеджерах, отчёт в Allure и Test IT, доступ к БД и Kafka через свои клиенты. Из него можно взять структуру файлов и идиомы.
- **Готовые источники дефектов.** Замечания выше — настоящие, а не придуманные: проверка Kafka без привязки к клиенту, SQL в f-строке, часовой пояс, зашитые даты, название теста шире проверок. Их можно закладывать в задание, переписав код так, чтобы его не узнали.
- **Готовые ловушки.** Повтор с `retrying` вместо паузы, финализатор для удаления данных, пул пользователей по группе xdist выглядят непривычно, но корректны.
- **В примерах не используется Playwright.** Мобильный тест работает через Appium, бэкенд-тест — через API и Kafka. Если для 1д нужен веб на Python + Playwright, образец придётся искать отдельно.
