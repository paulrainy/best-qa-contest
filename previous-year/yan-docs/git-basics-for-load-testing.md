# Основы работы с Git в НТ: выжимка

Выжимка из документа «Основы работы с Git в НТ_KEA». Учебный модуль для инженеров НТ: базовые операции Git, merge request в GitLab, разрешение конфликтов и запуск JMeter-скриптов, собранных как Maven-проект. В оригинале 46 скриншотов. Подразумевается, что Git Bash, JMeter и Maven уже установлены.

## Зачем Git команде НТ

В Git хранят скрипты, заглушки и утилиты и вместе работают над одними файлами. Модуль объясняет термины:

- **репозиторий** — папка под контролем Git;
- **коммит** — сохранённое изменение с хэшем и комментарием;
- **push** и **pull** — отправка своих и получение чужих коммитов.

Возможности Git: история в виде снимков, ветки для экспериментов, распределённость (полная копия истории у каждого), автоматическое слияние и конфликты.

## Базовые операции

| Операция | Команда или действие |
|---|---|
| Клонировать | GitLab → Code → Clone with HTTP; затем в Git Bash `git clone <url>` |
| Создать и переключить ветку | `git branch new_branch`, `git checkout new_branch` (список веток — `git branch`) |
| Закоммитить | `git add -A` (или `git add <файл>`), затем `git commit -m "…"`. Комментарий должен чётко описывать изменение |
| Запушить | `git push origin new_branch`, затем проверить ветку в веб-интерфейсе GitLab |

## Merge request в GitLab

Pull request (GitHub, Bitbucket, Azure DevOps) и merge request (GitLab) — одно и то же. В MR можно сделать ревью, оставить комментарии, прогнать CI/CD, поставить approve или отказ.

- **Title** — комментарий коммита; **Description** — описание изменений.
- **Assignee — автор.** Отвечает на комментарии, вносит правки, следит за прохождением CI/CD, решает, когда MR готов. В некоторых командах сам нажимает Merge.
- **Reviewer — более опытный коллега.** Проверяет ошибки, стиль и архитектуру, комментирует, ставит approve или отказ, проверяет исправления.
- Перед созданием проверить, какая ветка в какую вливается.
- В учебном примере автор сам себе и assignee, и reviewer: сам ставит Approve и сам нажимает Merge.

## Конфликты

Конфликт возникает в двух случаях: в двух ветках изменены одни и те же строки файла, или одна ветка удалила файл, а другая его изменила.

1. **Правка одной строки.** Merge в MR блокируется: «Merge blocked: merge conflicts must be resolved». Нажать «Resolve conflicts», выбрать вариант, затем «Commit to source branch». После этого MR можно вливать.
2. **Удаление и правка.** GitLab предлагает только «Merge locally». Порядок действий:
   - `git clone …`, `cd example/`;
   - `git pull origin branch_with_conflict`;
   - Git сообщает, что файл удалён в master;
   - `git add README.md`, `git commit -m "… resolved delete/modify conflict - kept file"`;
   - `git push origin`.

## JMeter как Maven-проект (из Git Bash)

| Команда | Что делает |
|---|---|
| `mvn clean` | Очищает `target` |
| `mvn jmeter:configure` | Собирает готовый JMeter с нужными плагинами |
| `mvn jmeter:gui` | Запускает GUI, удобно для правки скрипта |
| `mvn jmeter:jmeter -DselectConfiguration=default-cli` | Non-GUI запуск. Без дополнительных параметров делает одну итерацию |

Папку со скриптом советуют держать на рабочем столе, «чтобы не было конфликта с системными переменными».

## Замечания

- При разрешении конфликта «удаление и правка» результат пушат прямо в master, в обход MR и ревью. Обычно делают иначе: вливают master в исходную ветку, решают конфликт там и пушат исходную ветку, после чего MR проходит штатно.
- Самоапрув в учебном примере честно назван учебным, но стоит явно сказать, что в реальной работе так нельзя.
- `git checkout <ветка>` работает, но сейчас для переключения веток рекомендуют `git switch`, а для создания с переключением — `git switch -c`.

## Что полезно для конкурса

Материал вводный и для конкурса слабый. Пригодится разве что как контекст: скрипты НТ живут в GitLab как Maven-проекты JMeter (jmeter-maven-plugin). Это совпадает с нашим решением делать НТ-материалы в .jmx.
