# Логирование: понятие, уровни, механизмы: выжимка

Выжимка из документа «Логирование понятие, уровни, механизмы_KEA». Это теоретический модуль для инженеров НТ.

## Что такое лог

Лог — хронологическая запись значимой информации о работе системы: кто и когда что сделал, как система отреагировала, какие возникли ошибки, плюс метрики и отладочная информация.

## Типы логов

| Тип | Как выглядит | Как читать | Применение в НТ |
|---|---|---|---|
| Неструктурированные (текст) | Однострочные: одна строка — одно событие. Многострочные: одно событие на много строк, например Java stack trace | Сверху вниз, чтобы быстро понять проблему. Снизу вверх, от точки входа по вызовам, чтобы понять контекст; без доступа к коду это мало что даёт | Ignite, Kafka, Cassandra, Elasticsearch периодически пишут в лог «снимок состояния» узла в формате «ключ=значение» |
| Структурированные (JSON, XML) | Каждое событие — набор полей «ключ-значение» | Через веб-интерфейсы: Kibana, Grafana, Splunk | Поля превращаются в графики (например, `response_time_ms`). По `trace_id` прослеживают путь транзакции через микросервисы и интеграции |
| Бинарные | Байты по внутреннему протоколу. cat и grep не помогут, нужен специальный софт | Специализированные GUI-инструменты | Глубокое профилирование: Java Flight Recorder, сетевые дампы Wireshark. Почти не нагружают систему и не создают «эффекта наблюдателя», в отличие от текстового логирования под нагрузкой |

## Уровни логирования

От самого критичного к самому подробному:

- **FATAL** — ошибка, после которой приложение завершается;
- **ERROR** — ошибка, которая мешает работе, но не роняет приложение;
- **WARN** — потенциальная проблема;
- **INFO** — штатные события: старт и остановка процессов, смена конфигурации;
- **DEBUG** — подробности для отладки;
- **TRACE** — максимальная детализация, вплоть до каждого вызова метода и потока.

Зачем нужны уровни: фильтровать сообщения, быстрее находить проблемы и снижать объём записи. Последнее важно для производительности.

## Инструменты (справочный раздел)

- **Локальные:**
  - lnav — консольный просмотр нескольких логов, архивов и временной линии, с SQL-запросами по журналам;
  - ripgrep — быстрый рекурсивный поиск;
  - jq — работа с JSON-логами;
  - Klogg — просмотр гигабайтных файлов;
  - LogExpert — Windows-просмотрщик с tail, фильтрами и подсветкой;
  - Log Parser 2.2 — SQL-подобные запросы к IIS, Event Log, CSV, XML.
- **Централизованные:**
  - Grafana Loki — индексирует метки, а не весь текст; удобен для Kubernetes;
  - SigNoz — логи, метрики и трассировки на OpenTelemetry;
  - ELK — Elasticsearch, Logstash или Beats, Kibana; силён в полнотекстовом поиске;
  - Graylog — централизованное управление логами;
  - Splunk — коммерческий, силён в поиске и расследовании инцидентов.

## Замечание

Совет читать stack trace «сверху вниз, основная проблема в самом начале» неполон. В Java первопричина обычно в последнем блоке `Caused by:`, а верхняя строка часто показывает лишь обёртку исключения.

## Что полезно для конкурса

- Хорошая основа для задания «разбери лог»: дать фрагмент лога со stack trace с цепочкой `Caused by` и спросить первопричину. Сюда же подходят вопросы, какой уровень логирования включать на нагрузочном прогоне и почему DEBUG и TRACE искажают результаты НТ.
- Для трека НТ полезны идеи «эффекта наблюдателя» и `trace_id` для сквозного анализа.
