# Работа с БД (SQL и DBeaver) в НТ: выжимка

Выжимка из документа «Работа с базами данных SQL и Dbeaver в НТ_KEA». Учебный модуль на примере системы CDI (MDM, PostgreSQL): что проверять в БД до нагрузочного теста, что собирать после и какие заявки заводить в СУИТ. SQL-запросы в оригинале даны скриншотами DBeaver, здесь они переписаны текстом.

## До нагрузочного теста

| Проверка | Как часто | Зачем |
|---|---|---|
| VACUUM и реиндекс всех таблиц главной схемы | Раз в релиз, сразу после установки сборки на стенд НТ | Исключить влияние раздутых таблиц, мёртвых кортежей и устаревших индексов. На проме эти работы тоже проводят |
| Размер БД и число записей | Раз в релиз, после вакуума | Объём на стенде НТ должен быть близок к прому. Хорошим считается 80–90 % по критичным таблицам |
| VACUUM отдельных таблиц | Перед каждым тестом | В CDI три таблицы (`mdm_main.c__inl_l`, `c__inl_s`, `c__treg`) забиваются за тест |
| Работает ли сбор логов БД | Перед каждым тестом | Чтобы после теста было что анализировать |
| Работает ли сбор PWR-отчёта | Перед каждым тестом | То же |
| Корректна ли запись пишущими сервисами | Если пишущий сервис дорабатывали | Один прогон скрипта в JMeter, затем поиск записи в БД и проверка полей |

### Вакуум и реиндекс по одной таблице

Скрипт генерирует список команд, по одной на таблицу. Тогда прерванный вакуум не откатывает уже обработанные таблицы.

```sql
-- vacuum по очереди
SELECT format('VACUUM FULL ANALYZE %s.%s;', schemaname, tablename)
FROM pg_tables WHERE schemaname = 'mdm_main';

-- REINDEX по очереди (нужен редко: VACUUM FULL и так перестраивает индексы)
SELECT format('REINDEX table %s.%s;', schemaname, tablename)
FROM pg_tables WHERE schemaname = 'mdm_main';
```

Результат копируют в новый редактор и запускают как скрипт (Alt+X).

- Запускать только без нагрузки на БД. Выполнение занимает от нескольких часов до суток, поэтому его планируют заранее.
- Прерванный скрипт можно перезапустить целиком. Другой вариант — удалить из него уже обработанные таблицы, их видно в журнале выполнения DBeaver.

### Размер и объём

```sql
SELECT pg_size_pretty(pg_database_size('mdm_nt'));                         -- вся БД
SELECT pg_size_pretty(SUM(pg_total_relation_size(schemaname||'.'||tablename))::bigint)
FROM pg_tables WHERE schemaname = 'mdm_main';                              -- схема
SELECT pg_size_pretty(pg_relation_size('mdm_main.c_party_masters')),       -- таблица без индексов
       pg_size_pretty(pg_indexes_size('mdm_main.c_party_masters')),        -- индексы
       pg_size_pretty(pg_total_relation_size('mdm_main.c_party_masters')); -- всё вместе с TOAST
SELECT count(*) FROM mdm_main.c_party_i WHERE dic_party_status = 'ACTIVE'; -- число карточек клиентов
```

### Логи и PWR (под учётной записью для PWR, права выдают по заявке)

```sql
SELECT pg_current_logfile();                                               -- имя текущего лог-файла
SELECT * FROM pg_catalog.pg_read_file('pg_log/pg.260527.log', 0, 1000000000);
SELECT get_report(tstzrange('2026-05-27 04:30:00', '2026-05-27 11:20:00+03'));  -- PWR-отчёт за интервал, HTML
```

### Проверка пишущего сервиса

Пример — сервис `cdiCreatePerson`. Запускают одну итерацию в JMeter, берут id из ответа и ищут запись: `SELECT * FROM mdm_main.c_party_i WHERE source_id = '…'`. Затем сверяют ФИО, паспортные данные и прочие поля.

## После нагрузочного теста

Те же запросы для логов и PWR, только за интервал теста. Результат сохраняют в файлы: логи в .txt, PWR в .html.

## Заявки в СУИТ по БД

Типовые запросы в рамках НТ: снять PWR или AWR, снять логи, выполнить вакуум или реиндекс, изменить параметры БД. Путь: «Мои заявки» → «Каталог услуг» → группа PostgreSQL → услуга (например, «Выполнить VACUUM FULL на логических объектах СУБД PostgreSQL Тест») → тема и описание. Полный список услуг есть в [suit-requests.md](suit-requests.md).

## Замечания

- В запросе PWR у первой границы интервала нет часового пояса, а у второй стоит `+03`. Первая граница возьмёт пояс сессии, и при поясе сессии, отличном от МСК, интервал сместится.
- В комментарии к `pg_read_file` сказано «количество строк», но третий аргумент — это число байт.
- Довод «вакуум всех таблиц одной командой — это одна транзакция с откатом» для PostgreSQL неточен: `VACUUM` вообще нельзя выполнить внутри транзакционного блока. Сама практика «по одной таблице» при этом правильная: её удобно прерывать и продолжать.

## Что полезно для конкурса

- Это готовый материал для SQL-части трека НТ. Можно спросить, что проверить в БД перед тестом, почему 80–90 % объёма прома и зачем вакуум перед каждым прогоном.
- Подходит и задание на ревью скрипта подготовки стенда: VACUUM FULL под нагрузкой, интервал PWR без часового пояса, проверка записи без сверки полей.
