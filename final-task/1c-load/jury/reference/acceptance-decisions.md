# Решения при исполнении нагрузочного плана

Исполнение разрешено пользователем 11.11.2026 после завершения Python. Работа остаётся в `feat/final-reference-solutions`; основание текущего нагрузочного этапа — d8e7ca3. Отдельная ветка/рабочая копия для реализации не создавалась по ранее указанному порядку пользователя. Коммиты локальные до отдельной команды на публикацию.

## Принятые решения

- Старый статус «не согласовано» заменён текущим разрешением начать. Объём соответствует четырём этапам согласованного плана, шкала оценки остаётся отдельной работой. Цена ошибки — неверное прочтение разрешения; пользователь прямо попросил начать нагрузку и продолжить план.
- Используется существующая рабочая ветка. Цена — история включает три предыдущих эталона; новая нагрузочная работа отделяется диапазоном от d8e7ca3.
- Служебный помощник разбирает только заголовки Task N; русские этапы извлечены в журнал без переформулирования. Цена — ручная сверка границ этапов вместо автоматического извлечения.
- Matplotlib 3.9.2 был исходным ориентиром плана; для колёс современных CPython выбран 3.11.2. NumPy и Contourpy закреплены маркерами версий с сохранением Python 3.11. Цена — разные транзитивные версии в разных интерпретаторах, фактический набор записывается отдельно; измерительные формулы используют stdlib.
- В конце Open Model расписания есть 35 секунд без новых arrivals: последний HTTP имеет timeout 30 секунд. Официальное `jmeterengine.force.system.exit=true` завершает CLI после теста/HTML без ожидания служебного пула. Цена — длительность процесса больше измерительного интервала; хвост в бизнес-RPS не входит.
- Контроль недодачи использует задержку dispatch в генераторе перед HTTP вместо изменения продукта. Цена — подтверждается обнаружение запоздалой подачи, а не поведение при настоящем исчерпании CPU/RAM. JAR не менялся, изменённый JMX сохранён отдельно.
- Полные профили выполняются только на Java 17/Python 3.11. Совместимость проверяется пятью Python на Java 17 и базовым Python на Java 21, со сменой JVM и стенда, и генератора. Цена — не проверено полное произведение 5×2; это не заявляется. Установка, сбор, анализ и PNG проверяются в каждом выбранном сочетании.
- Ревью нового нагрузочного этапа использует диапазон d8e7ca3..HEAD; ранее принятые Java/ручной/Python не переаудируются. Цена — их прежние границы приёмки остаются в собственных отчётах.

## Решения независимого повтора 12.11.2026

- Повтор выполнен отдельной сессией агента на Windows 11 AMD64 с Python 3.11.18 из uv: так указал пользователь («гоняй на джаве 25, а питон ставь любой через uv»). Цена — исполнитель знал авторский отчёт; поэтому числа пересчитаны отдельным скриптом, а человеческая проверка и ВДИ не заявляются.
- Стенд запущен на Java 25.0.5. Генератор на Java 25 невозможен: Groovy 3.0.20 из JMeter 5.6.3 не компилирует JSR223, прогон дал 0 POST. Генератор переведён на JRE 17.0.21 из того же комплекта JMeter, JMX не менялся. Цена — Java 25 подтверждена только для стенда; переписывать JMX без Groovy значило бы обесценить авторские основные прогоны.
- Сбор ресурсов генератора в Windows реализован через WinAPI из stdlib, без psutil. Цена — CPU в Windows измеряется за интервал между замерами, а не как ps; различие описано в методике.
- Повторены только smoke, confirmation и raw CLI, как требует план. Steps и stability на этой машине не повторялись.
- `evidence/raw-cli/jmeter.log` из SHA256SUMS удалён: файл не попал в Git. Восстановить его можно только с машины автора; для таких логов добавлено исключение в `.gitignore`.
- В raw CLI повтора сохранён только `statistics.json` HTML-отчёта, без 3 МБ стандартных ресурсов JMeter.
