# Независимый повтор нагрузочного эталона на Windows

12.11.2026. **Smoke и confirmation повторены; авторские выводы о p95 и SLO воспроизведены на другой ОС и другом оборудовании.** По ходу повтора исправлены четыре проблемы инструментария под Windows и одна в составе доказательств. Неустранимое здесь ограничение — JMeter 5.6.3 со встроенным Groovy не работает на Java 25, поэтому генератор запускался на Java 17.

## Кто и как повторял

Исполнитель — отдельная сессия агента Claude на другой машине, не автор эталона. Это не проверка человеком-коллегой и не пилот ВДИ. Порядок взят из [README эталона](../../../README.md): health, reset, `run.py` с новым каталогом, затем raw CLI. Исполнитель заранее читал отчёт автора. Поэтому числа пересчитаны отдельным [recount.py](recount.py): он не использует формулы `analyse.py` и сверяет с ними только итог.

## Наблюдение: холодный старт на слабой машине

В первые 10 секунд confirmation p95 был 2401 мс: 489 из 533 POST дольше 500 мс, 250 переводов завершились позже 2 с. Очередь учёта к 13-й секунде выросла до 185. Генератор в это время занимал около 200% CPU (два из четырёх логических CPU) и создал до 640 потоков, у автора их было 43. С 20-й секунды всё стабильно: p95 в [20;30) — 6 мс, очередь 0.

Измерительная когорта [30;180) по методике этот участок не включает, и вердикт законен. Если бы прогрев не исключали, p95 всех 9000 POST составил бы 710 мс — FAIL по порогу 500 мс, хотя доля в срок осталась бы 96,9%. Вывод для жюри: исключение прогрева должно опираться на наблюдаемую стабилизацию. При совмещённом генераторе на двухъядерном ПК эти данные не позволяют разделить задержку стенда и генератора на холодном старте. Smoke по той же причине дал p95 124 мс, у автора — 12 мс.

## Найдено и исправлено

1. **Сбор ресурсов генератора в Windows.** Раньше там вызывался `ps`, в metrics.csv писался `generatorError`, а runner возвращал 2. Теперь `collect_metrics.py` берёт дочерний `java.exe` лаунчера через WinAPI из stdlib (Toolhelp, GetProcessTimes, K32GetProcessMemoryInfo). CPU — доля одного ядра за интервал между замерами, память — рабочий набор. Добавлен тест на интервальный CPU; на Windows проходят 18/18 тестов.
2. **Выбор JVM генератора.** `jmeter.bat` вызывает `java.exe` из PATH и игнорирует `JAVA_HOME`. Runner теперь ставит `JAVA_HOME\bin` первым и пишет `javaOnPath` в environment.json.
3. **Зависание и «осиротевший» процесс.** При ошибке `jmeter.bat` выполняет `pause`: stdin закрыт, чтобы он не ждал клавишу. Остановка выполняется через `taskkill /T`, иначе `java.exe` переживает свой `cmd.exe`.
4. **Кириллица.** В Git Bash и при перенаправлении Python печатал в cp1252 и падал на кириллице. Точки входа инструментов теперь пишут UTF-8. Для Windows в environment.json добавлены сведения о CPU/RAM/ОС и командной строке стенда, а сообщение о прогоне без POST стало конкретным.
5. **SHA256SUMS.** Список указывал на `evidence/raw-cli/jmeter.log`, которого нет в Git: файл отфильтровал `.gitignore`. Строка удалена, для отобранных логов добавлено исключение, см. [evidence/README](../../README.md).

## Не исправлено и границы

- **JMeter 5.6.3 на Java 25.** Встроенный Groovy 3.0.20 не компилирует JSR223 на файлах классов версии 69: [groovy-java25.txt](generator-java25/groovy-java25.txt). Потоки Open Model стартуют и завершаются без единого сэмпла, ERROR в jmeter.log нет, JMeter возвращает 0. Ошибку ловит только runner: 0 POST, код 1. Эталонный JMX требует для генератора Java 17 или 21. Убрать Groovy из JMX штатными экстракторами и assertions можно, но тогда основные авторские профили придётся повторить. Это решение организаторов.
- **Консоль стенда.** На Java 25 при перенаправлении в Git Bash кириллица выводится как «?», см. [stand-console.log](stand-console.log). На работу стенда это не влияет.
- **Не повторялось.** Steps и stability, Java 21 и другие версии Python на этой машине. Это не ВДИ и не проверка человеком; пилот на целевом окружении остаётся обязательным.
