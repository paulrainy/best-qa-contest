# Защита Python-эталона: 7 минут

1. **Цель и объём.** Построена автоматизация сервиса переводов с нуля. F01–F18 выбраны по рискам движения денег, лимитов/комиссии, повторов и асинхронности. Количество дефектов и число методов не являются целью.
2. **Данные и точность.** Каждый сценарий создаёт собственных клиентов и счета через открытый тестовый API. `Decimal` хранит ожидаемые суммы; JSON содержит точное числовое значение. SQL только SELECT с параметрами, без подготовки данных через БД.
3. **Три границы системы.** HTTP проверяет пользовательский результат, временная AMQP-очередь подписывается до POST и отбирает собственный transferId, SQL подтверждает деньги и единственность проводок. HTTP202 сам по себе не доказывает завершение.
4. **Сложные правила.** Комиссия 100 после 90000+20000; HALF_UP30,005→30,01; FAILED возвращает 40400 после 40000+400;24 часа считаются от собственного createdAt. Матрица 18 статусов и денежные границы выполняются на независимых данных.
5. **Асинхронность и очистка.** Ожидания имеют предел и ID в ошибке. Пауза учёта показывает PROCESSING, возобновление — один кредит. Глобальные сценарии последовательны, восстанавливают реальные часы/потребителей в finally; исключение проверено и на помощнике, и на реальном стенде.
6. **Воспроизводимость и вывод.** Один lock-файл, Python3.11–3.15, Java 17/21,64 интеграционные и 11 unit-проверок. Полный XML сверяется по точному каталогу; старые файлы не переиспользуются. Доказательства и ограничения — в отчёте. Mac не подтверждает Windows/ВДИ или НФТ; DLQ и повторная доставка требуют отдельной работы.

Вопросы 3 минуты: почему нужны все три интерфейса; как отделяется ошибка окружения от дефекта; какие риски остаются; что изменится при добавлении нового стабильного Python; какой осмысленный частичный результат можно оценить без счётчика найденных дефектов.
