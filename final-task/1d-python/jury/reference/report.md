# Результаты Python-эталона

11.11.2026. Реализован самостоятельный проект pytest по ТЗ2.0 и F01–F18. Бизнес-ожидания десятичные, API передаёт деньги числом; AMQP и PostgreSQL проверяются на реальном готовом стенде. Стенд в ходе Python-плана не менялся. Независимая приёмка ожидается отдельно от авторских результатов ниже.

## Сборка и установка

Готовый JAR SHA-256 `2f0158dc67efd6ffec84bc0302c9201407f7f1a8f10eb4f093c8f7e55d199aed`, тот же для Java17/21. Базовая сборка Temurin17.0.21+9, compiler release17; [манифест](../../../jury/stand-manifest.md). Окружение исполнения — macOS27.2 ARM64, Java17.0.21 и21.0.13.0.3, uv0.10.6. [Версия17](evidence/java17/version.txt), [версия21](evidence/java21/version.txt).

`requires-python = ">=3.11"`, базовая `.python-version`3.11. Один `uv.lock` SHA-256 `7fb0af5ec8fd629a9f563744135b9907ff67593ede2375210ba4acd2f4b3747c`; pytest9.1.1, requests2.34.2, pika1.4.4, psycopg/binary3.3.8. На каждом Python сначала создано отдельное чистое окружение через `uv sync --locked --python <интерпретатор>`, затем выполнены помощники и полный интеграционный набор. Те же окружения повторно использованы с Java21; JAR не пересобирался.

По [официальному списку Python](https://www.python.org/downloads/) на дату приёмки стабильные поддерживаемые ветки начиная с3.11 —3.11–3.15,3.16 ещё pre-release. Проверены указанные ниже реальные patch-версии, они не объявляются последними исправлениями каждой ветки. После выхода нового стабильного Python матрицу нужно повторять.

## Проверка данных и диагностики

Дополнительный полный авторский прогон3.11/Java21 —63 PASS: [XML](evidence/author-sql/full/results.xml), [HTTP](evidence/author-sql/http.jsonl). По его собственным125 счетам и47 принятым переводам выполнена [SQL-сверка](evidence/author-sql/sql.json): остаток равен сумме проводок; COMPLETED имеет ровно один кредит суммы, FAILED — ровно один полный возврат суммы+комиссии без кредита получателю. Нарушений0. Сверка не включает чужие переводы или всю историю стенда.

Контроли воспроизводимости — [controls.json](evidence/author-sql/controls.json):

- недоступный PostgreSQL-порт даёт setup ERROR, pytest1 и явную причину «БД недоступна»; ошибка не считается продуктовым дефектом;
- существующий путь XML отклоняется до запуска: pytest4, старый файл не изменён;
- анализатор отклоняет отсутствие теста, failure, error/timeout, skip, дубликат и пустой каталог; полный зелёный XML принимает;
- после исключения в глобальном сценарии восстановлены часы/оба потребителя, закрыты PostgreSQL и AMQP; это проверено реальным `test_scope_restores_after_exception_and_connections_close` во всех10 прогонах;
- итоговый контроль после диагностики — COMPLETED, остатки999900/100, реальные часы и оба RUNNING: [HTTP](evidence/author-sql/final-control-http.jsonl).

## Соответствие и границы

[Трассировка](traceability.md) покрывает все18 общих групп на глубине Java и ручного решения. Дополнительные проверки верхней границы комиссии и MF01 дают63 интеграционных testcase вместо61 в Java; это не требование к количеству тестов участника. Вспомогательные11 unit-проверок отделены от каталога полного интеграционного набора. Нет skip/xfail, известных допустимых падений, прямой записи в БД, чтения внутренних классов стенда или подмены JAR.

Для одновременных BLOCKED/CLOSED принимается один из применимых422-кодов: ТЗ не задаёт приоритет. Адресат уведомления проверяется URL клиента и SQL, не неописанным полем clientId в JSON. Общая роль `qa` и запрет записи на стороне сервера ранее проверены общими средствами; Python-клиент дополнительно не отправляет SQL кроме SELECT. [Открытые риски](known-findings.md).

Windows/ВДИ AMD64, производительность/НФТ, гонки, повторная доставка, три попытки/DLQ, инфраструктурные отказы и длительная эксплуатация этим проектом не подтверждены. Нагрузочный план отложен пользователем; он не выполнялся. Намеренные дефекты не внедрялись, балльная шкала не создавалась.

Для будущей шкалы наблюдаемы: связь требования с реальной проверкой, независимые данные, проверка денег/проводок вместо одного HTTP-кода, собственное AMQP-событие, ограниченные ожидания, cleanup при ошибке, повторяемая установка и честный отчёт. Частично выполненный проект можно различать по этим результатам; веса и штрафы требуют отдельного согласования после четырёх эталонов.
