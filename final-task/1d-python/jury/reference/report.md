# Результаты Python-эталона

11.11.2026. Реализован самостоятельный проект pytest по ТЗ2.0 и F01–F18. Бизнес-ожидания десятичные, API передаёт деньги числом; AMQP и PostgreSQL проверяются на реальном готовом стенде. Стенд в ходе Python-плана не менялся. Независимая приёмка первоначального набора63 пройдена. После замечания к точной половине копейки набор усилен до64; итоговая матрица64 выполнена автором, новый вариант отдельно независимо не повторялся.

## Соответствие и границы

[Трассировка](traceability.md) покрывает все18 общих групп на глубине Java и ручного решения. Дополнительные проверки верхней границы комиссии, MF01 и точной половины копейки дают64 интеграционных testcase вместо61 в Java; это не требование к количеству тестов участника. Вспомогательные11 unit-проверок отделены от каталога полного интеграционного набора. Нет skip/xfail, известных допустимых падений, прямой записи в БД, чтения внутренних классов стенда или подмены JAR.

Для одновременных BLOCKED/CLOSED принимается один из применимых422-кодов: ТЗ не задаёт приоритет. Адресат уведомления проверяется URL клиента и SQL, не неописанным полем clientId в JSON. Общая роль `qa` и запрет записи на стороне сервера ранее проверены общими средствами; Python-клиент дополнительно не отправляет SQL кроме SELECT. [Открытые риски](known-findings.md).

Windows/ВДИ AMD64, производительность/НФТ, гонки, повторная доставка, три попытки/DLQ, инфраструктурные отказы и длительная эксплуатация этим проектом не подтверждены. Нагрузочный план отложен пользователем; он не выполнялся. Намеренные дефекты не внедрялись, балльная шкала не создавалась.

Для будущей шкалы наблюдаемы: связь требования с реальной проверкой, независимые данные, проверка денег/проводок вместо одного HTTP-кода, собственное AMQP-событие, ограниченные ожидания, cleanup при ошибке, повторяемая установка и честный отчёт. Частично выполненный проект можно различать по этим результатам; веса и штрафы требуют отдельного согласования после четырёх эталонов.
