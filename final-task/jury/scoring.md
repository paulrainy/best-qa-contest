# Шкала оценки финала — предложение

Черновик для согласования с жюри.

## Принцип: «найди, докажи, защити»

Чем отличается от прошлогодней шкалы:

- **Вес по важности, а не 0/1.** Гонка при списании весит больше, чем неверное округление.
- **Баллы только за доказанное.** Дефект без воспроизводимых шагов и доказательства не засчитывается, даже если в ключе он есть.
- **Штраф за ложные находки.** Поведение по ТЗ, оформленное как дефект, стоит −1. Это отсекает стратегию «написать побольше».
- **Равный максимум для всех треков.** У каждого трека по три своих дефекта по 5 баллов.
- **90 баллов из 100 считаются по ключу и чек-листу до финала.** На сцене оценивается только защита — 10 баллов. Так меньше зависимость от харизмы и от того, кто выступает первым.

## Разделы

| Раздел | Баллы | Как считается |
| --- | --- | --- |
| 1. Анализ ТЗ | 15 | По ключу, раздел 1 `answer-key.md` |
| 2. Дефекты стенда | 40 | По ключу, раздел 2: общие — по 3, свой трек — по 5, чужие треки и Б1 — по 2 (не больше 10) |
| 3. Работа по треку | 25 | Чек-лист ниже: 5 пунктов по 0, 2 или 5 |
| 4. SQL-сверка | 10 | По ключу, раздел 4: по 2 за проверку |
| 5. Защита | 10 | Презентация — 4, ответы на вопросы — 6 |
| Ловушки | до −5 | По ключу, раздел 3: −1 за каждую |
| **Итого** | **100** | |

При равенстве баллов выше тот, у кого больше в разделе 2, затем в разделе 5.

## Порядок оценки

1. Участники сдают материалы за 5 рабочих дней до финала.
2. Два члена жюри независимо оценивают разделы 1–4 и ловушки по ключу и чек-листу, потом сверяют расхождения и договариваются.
3. На финале каждый член жюри оценивает раздел 5, в зачёт идёт среднее, округлённое до целого.
4. Итог — сумма.

## 3. Работа по треку — 25 баллов

Каждый пункт: **5** — сделано полностью, **2** — частично или с заметными пробелами, **0** — нет.

### Ручное тестирование

| № | Пункт |
| --- | --- |
| Р-1 | Техники тест-дизайна применены к правилам ТЗ, и это видно из материалов: границы суммы, лимита и порога; классы эквивалентности статусов счёта; таблица решений «статус отправителя × статус получателя × вид перевода»; переходы состояний перевода |
| Р-2 | Покрытие прослеживается до ТЗ: у кейсов есть ссылка на раздел, разделы 2–9 покрыты |
| Р-3 | Кейсы воспроизводимы другим человеком: предусловия, конкретные данные, конкретные ожидаемые результаты; данные готовятся через тестовый API |
| Р-4 | Асинхронная часть исследована: использованы пауза потребителей, тестовые часы, консоль брокера и БД; есть отчёт о сессиях — цель, что сделано, что найдено |
| Р-5 | Приоритеты: что проверять первым при нехватке времени и почему, состав регресса |

### Автоматизация

| № | Пункт |
| --- | --- |
| А-1 | Тесты запускаются одной командой по инструкции и независимы: сами готовят данные, не зависят от порядка запуска и от исходных данных стенда |
| А-2 | Проверки на трёх уровнях: ответ API, событие в брокере (состав и значения полей), данные в БД |
| А-3 | Параметризация и генерация данных: границы, перебор сумм и комбинаций, а не один тест на одно значение |
| А-4 | Сценарии, недоступные руками: параллельные запросы, повторная доставка, битые сообщения и DLQ |
| А-5 | Падение понятно без отладки: осмысленные сообщения проверок, отчёт (Allure или аналог), ожидания по условию вместо пауз |

### Нагрузочное тестирование

| № | Пункт |
| --- | --- |
| Н-1 | Методика: цель, профиль (какие запросы и в какой доле, откуда доли), модель нагрузки (открытая или закрытая, пейсинг), критерии успеха из НФТ, длительность |
| Н-2 | Скрипт проверяет ответы — код и тело — и готовит данные так, чтобы не упираться в лимиты и остатки: разные клиенты из CSV, уникальный `Idempotency-Key` |
| Н-3 | Набор тестов: поиск максимальной производительности (ступени), подтверждение НФТ, стабильность (длительный прогон) |
| Н-4 | Мониторинг: глубина очереди, скорость обработки, время до финального статуса, ресурсы JVM, рост таблицы переводов — сопоставлены с нагрузкой по времени |
| Н-5 | Выводы подтверждены данными: максимальная интенсивность, узкое место, прогноз на объём из НФТ, рекомендации |

## 5. Защита — 10 баллов

### Презентация — 4 балла

| Пункт | Баллы |
| --- | --- |
| Начинает с главного риска, а не с перечня баг-репортов | 1 |
| Решение о выпуске: 2 — «не выпускать», названы блокеры и что можно исправить после релиза; 1 — решение без разделения на блокеры и остальное; 0 — нет решения или «выпускать» | 2 |
| Уложился в 7 минут | 1 |

### Ответы на вопросы — 6 баллов

Три вопроса по 2 балла: **2** — ответ содержит основные пункты из `questions.md`, **1** — частично, **0** — нет ответа или ответ неверный. Первый вопрос — всегда «вопрос на изменение» из `questions.md`, остальные два жюри выбирает по материалам участника.
