# Подготовка данных и очистка

Базовый URL `http://localhost:18400`. Настройки и подключения — в [README участника](../../participant/README.md). Все запросы и объяснения ниже — инструкция исполнителю, не готовый набор автотестов.

## Независимая пара P

1. `POST /api/test/accounts` с `{"balance":1000000.00,"status":"ACTIVE"}` →201. Сохранить из ответа `accountNumber=A`, `clientId=CA`.
2. Для OTHER: `POST /api/test/accounts` с `{"balance":0.00,"status":"ACTIVE"}` →201, сохранить `B,CB`. У `CA` и `CB` разные значения.
3. Для OWN: второй запрос с `{"balance":0.00,"status":"ACTIVE","clientId":"<CA>"}` →201; `B` принадлежит тому же клиенту.
4. Зафиксировать исходные остатки из ответов создания: A=1000000,00, B=0,00. При дополнительной подготовке или сомнении заново прочитать оба счёта перед переводом. Подставлять значения из собственных ответов, не номера из доказательств автора.

`POST /api/v1/transfers`, заголовки `Content-Type: application/json`, `Idempotency-Key: <новая непустая строка <=100 символов>`, тело `{"fromAccount":"<A>","toAccount":"<B>","amount":100.00}`. Числа не заключать в кавычки. Сохранить весь ответ и `transferId=T`. Повторять ключ только в кейсах идемпотентности.

`GET /api/v1/transfers/<T>`: наблюдать финал до 10 с, фиксируя время наблюдения. PROCESSING по истечении срока — отдельный исход, не FAILED. Проверить остатки `GET /api/v1/accounts/<A/B>` и проводки `GET /api/v1/accounts/<A/B>/operations`, фильтруя по T; для начального остатка transferId=NULL. Для SQL использовать читающий `qa/qa`, H2 URL `jdbc:h2:tcp://localhost:19400/mem:stand`, H2 driver2.5.252.

## Приёмы подготовки

- Статус своего счёта: `PUT /api/test/accounts/<A>/status`, `{"status":"BLOCKED"}` или CLOSED/ACTIVE. В матрице статусы изменяются только у пары этого кейса; до/после каждого варианта фиксируются остатки.
- Ровно исчерпать бесплатный порог: свежая OTHER-пара, завершить 100000,00. После этого A=900000,00, B=100000,00, комиссия 0,00.
- Лимит без влияния пересечения комиссии: на отдельном стенде поставить 20.06.2030 по МСК, подготовить предыдущий перевод 100000,00; поставить 21.06.2030, выполнить проверяемую сумму. Для каждого варианта — новый клиент.
- F16: только успешные 100000,00, затем на паузе 40000,00 с комиссией 400,00. Не использовать 90000+20000 в подготовке. Остаток сравнивать непосредственно перед вторым запросом, а не с начальным миллионом.
- Часы: сначала сохранить `GET /api/test/clock` и потребителей `GET /api/test/consumers`. `PUT /api/test/clock`, `{"now":"2031-10-15T23:59:00+03:00"}`; время после PUT продолжает идти. Подготовить счета до смены времени, чтобы успеть исполнить шаги до границы.
- Истечение ключа M13: отсчитать 24 ч от `createdAt` ответа первого POST, а не от времени предыдущего PUT часов. Для проверки после истечения поставить `createdAt + 24 часа + 1 минута`, затем сверить `now` через GET часов. Фиксированное время следующего дня может оказаться слишком ранним, если первый POST был выполнен с задержкой.
- Оборот: выбрать две соседние свободные даты, проверить `GET /api/v1/reports/turnover?date=<дата>` для обеих →0 переводов. Если даты заняты, выбрать другие. Не рассчитывать на дату из прошлой сессии.
- AMQP: в веб-консоли Qpid создать свою временную очередь, привязать к `transfers` ключом `transfer.created` ДО запроса; прочитать копию события по собственному T. Рабочую очередь учёта не потреблять. Удалить свою очередь после сохранения доказательства.

## C01 — обязательная очистка и контроль

В конце любого глобального кейса, включая остановку из-за ошибки:

1. `POST /api/test/consumers/accounting/resume` и `/notifications/resume` →200.
2. `DELETE /api/test/clock` →200, shifted=false (для этой сессии исходное состояние — реальные часы и оба RUNNING).
3. `GET /api/test/consumers` →оба RUNNING; `GET /api/v1/health` →UP, clockShifted=false. Проверить незавершённые собственные операции и дождаться финала.
4. На новой OWN-паре выполнить 100,00, дождаться COMPLETED<=10 с; A=999900,00, B=100,00, нулевая комиссия. Сохранить контроль.

Reset не использовать как замену очистки: он уничтожает данные всех кейсов и доказательства в БД. Один reset перед полной сессией допустим. Созданные счета остаются данными этой сессии; удалять их напрямую из БД нельзя.

## Чтение собственной копии события через Qpid REST

Это ручные HTTP-действия вместо написания AMQP-клиента. Официальный [REST API Qpid10.1.1](https://qpid.apache.org/releases/qpid-broker-j-10.1.1/book/Java-Broker-Management-Channel-REST-API.html) и `/apidocs` доступны в консоли. В примерах `Q` — своё уникальное имя, автор использовал `manual-m14-20261110`; авторизация `guest/guest`, базовый адрес `http://localhost:15672`.

1. PUT `/api/latest/queue/default/default/<Q>`, тело `{"durable":false}` →201. POST `/api/latest/exchange/default/default/transfers/bind`, `{"destination":"<Q>","bindingKey":"transfer.created"}` →200 true. Сначала привязка, затем перевод продукта.
2. GET `/api/latest/queue/default/default/<Q>/getMessageInfo` →массив; сохранить числовое `id` нужной копии. Не путать его с UUID transferId внутри тела.
3. GET `/api/latest/port/HTTP`: сохранить `allowConfidentialOperationsOnInsecureChannels` (исходно false) и убедиться, что bindingAddress=localhost. При false чтение тела через HTTP даёт 403. Только на этом локальном учебном стенде перед просмотром PUT того же порта с `{"allowConfidentialOperationsOnInsecureChannels":true}`; логин и привязка к localhost сохраняются. Альтернатива — свой обычный AMQP0-9-1 клиент, тогда настройка HTTP не нужна.
4. GET `/api/latest/queue/default/default/<Q>/getMessageContent?messageId=<числовой id>&returnJson=true` →JSON-строка с телом события. Раскрыть строку, сопоставить transferId/счета/денежные поля с собственным запросом.
5. Сразу, в том числе при ошибке чтения, вернуть сохранённое значение параметра порта, проверить его GET. DELETE своей очереди, затем GET неё→404. Изменять аутентификацию, адрес привязки или рабочие очереди не требуется.

В M14 исходное false восстановлено, собственная очередь удалена. Состояние порта входит в очистку именно этого кейса; C01 отвечает за часы и потребителей.
