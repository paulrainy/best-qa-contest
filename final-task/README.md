# Финальный кейс «Сервис переводов»

Черновик финального задания номинации «Лучший тестировщик». Участник получает ТЗ и работающий стенд — чёрный ящик: сервис переводов с API, брокером сообщений (совместим с RabbitMQ), учётом, уведомлениями и БД. Задача — найти проблемы в ТЗ и дефекты в стенде, сверить данные SQL-запросами, решить, выпускать ли сервис, и защитить решение за 7 минут.

## Идея

- **Одна система — три трека.** Ручной тестировщик, автоматизатор и нагрузочник работают с одним стендом. В нём есть общие дефекты и по три дефекта, которые проще найти инструментами своего трека.
- **Нейросеть не решает за участника.** Ответ нельзя получить, прочитав ТЗ: стенд нужно запускать и исследовать. Часть дефектов видна только при параллельных запросах, повторной доставке сообщений, переходе через полночь или под нагрузкой.
- **Оценка в основном по ключу.** 90 баллов из 100 считаются по ключу и чек-листу до финала, на сцене — только защита.

## Структура

```
participant/                — отдаём участникам (архивом, после сборки стенда)
  case.md                   — условие кейса: задание, что сдать, правила
  spec.md                   — ТЗ с заложенными проблемами
  stand/                    — стенд: transfer-stand.jar + lib/ (собираются скриптом), run.cmd, run.sh, README
  starters/java/            — каркас автотестов: JUnit 5, RestAssured, amqp-client, H2
  starters/python/          — каркас автотестов: pytest, requests, pika, psycopg
jury/                       — только жюри
  answer-key.md             — ключ: замечания к ТЗ, дефекты стенда, ловушки, SQL-сверка
  scoring.md                — шкала оценки (предложение)
  questions.md              — вопросы на защите и что должно прозвучать в ответе
  sql/reconciliation.sql    — эталонные сверочные запросы
  verify/                   — скрипты, которые воспроизводят дефекты на запущенном стенде
  stand-src/                — исходники стенда, дефекты помечены «ДЕФЕКТ»; участникам не передавать
  build-stand.sh            — сборка обфусцированного стенда в participant/stand/
```

## Стенд

Один процесс на Java 17+, ничего не устанавливается, Docker не нужен:

- HTTP API — на JDK HttpServer;
- брокер — встроенный Apache Qpid Broker-J 10. Это не RabbitMQ, но протокол тот же (AMQP 0-9-1): клиенты RabbitMQ (`amqp-client`, `pika`) работают с ним без изменений. Веб-консоль своя;
- БД — H2 в памяти. Участникам открыта только на чтение: по протоколу H2 (DBeaver, JDBC) и по протоколу PostgreSQL (psycopg);
- данные — 2000 клиентов, 30 000 переводов истории; сбрасываются тестовым API.

Код обфусцирован ProGuard: классы и методы переименованы в `a`, `b`, `c`. Это затрудняет чтение, но не делает его невозможным. Упорный участник с декомпилятором и нейросетью восстановит логику. Поэтому в правилах прямо запрещено изучать код стенда, а находки, полученные так, не засчитываются.

### Сборка

Нужны JDK 17+ с каталогом `jmods` и Maven:

```bash
bash final-task/jury/build-stand.sh
```

Собранные `transfer-stand.jar` и `lib/` (около 40 МБ) в git не хранятся — после сборки папку `participant/` целиком архивируем и отправляем.

### Проверка ключа

Запустить стенд (`participant/stand/run.sh`), затем:

```bash
cd final-task/jury/verify
pip install -r requirements.txt
python verify_defects.py            # 12 функциональных дефектов: О1–О5, Р1–Р3, А1–А3, Б1
python verify_defects.py controls   # 6 контрольных сценариев: то, что по ТЗ должно работать
python load_check.py 60 150         # Н1 и Н3: 60 переводов/с, 150 с
python load_check.py 30 300         # Н2: рост времени ответа от объёма базы
```

Скрипты сбрасывают данные стенда.

Результаты на ноутбуке автора (Apple M-серии):

- все 12 функциональных дефектов воспроизводятся, все 6 контрольных сценариев проходят;
- Н1: учёт разбирает около 34 сообщений в секунду, при 60/с за 2 секунды завершилось 3,4 % переводов;
- Н3: ответы «200 REJECTED» появляются на 40–45-й секунде;
- Н2: p95 `POST` растёт примерно на 2 мс на каждую 1 000 переводов в базе, при 30/с за 5 минут — с 87 до 105 мс.

## Открытые вопросы

- **Java на ВДИ.** Стенд требует Java 17+. Если на ВДИ Java 11, придётся откатиться на Qpid 9.
- **Python на ВДИ** не проверен. Python-трек автоматизации необязателен: стенд от Python не зависит.
- **Производительность ВДИ.** Пороги Н1–Н3 подобраны на ноутбуке. Нужно запустить `load_check.py` на ВДИ: если стенд там заметно медленнее, уменьшить историю (`seed.history` в `stand.properties`) или пересобрать с другими задержками.
- **Даты.** Когда выдаём кейс и когда сдача. В `case.md` сейчас: сдача за 5 рабочих дней до финала.
- **Шкала** — предложение, нужно согласовать с жюри.
